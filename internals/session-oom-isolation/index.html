    Session OOM isolation

    An out-of-memory kill of a process running inside Contour — a compiler, a language server — must end that process and nothing else. This page explains why that took code, and how it works.

    Why Contour died with its children

    Desktops start applications as systemd units (app-org.contourterminal.Contour@….service). Every process a session spawns lands in that unit's cgroup, beside Contour. Two things then act on the unit as a whole:

    • OOMPolicy=stop (systemd's DefaultOOMPolicy): when the kernel OOM-kills any process in the unit, systemd stops the whole unit — Contour and every tab.
    • systemd-oomd kills whole cgroups under memory pressure, so a session's cgroup that contains Contour makes Contour a candidate.

    What happens now

    vtpty::Process::start() spawns the child through the spawn trampoline and parks it on a gate — a socket pair — before exec. The parent hands the child, as a ParkedChild, to the injected ProcessPlacement:

    • SystemdScopePlacement (Linux, CONTOUR_WITH_SYSTEMD=ON) asks the user's systemd, over sd-bus, for a transient contour-session-<contour pid>-<child pid>-<n>.scope in app.slice with OOMPolicy=continue, waits for the job, and releases the child. Everything the child forks from then on is born in that scope. Every placed process's scope is named so, and described -- as the log names it -- by what the process is to Contour (ProcessRole): a session's shell, a program a session started, the daemon, or the tmux client. systemd before 253 knows neither PIDFDs nor OOMPolicy= on scopes and refuses a request carrying either, so the first such refusal switches the connection to PIDs= and no OOMPolicy=. Its scopes do not react to an out-of-memory kill at all, which is what we want. A child released unplaced because the bus fell silent -- its request timed out, or the breaker held requests off -- is placed late: once a request may be sent again, the worker asks for a scope for the running process (by pidfd; by pid only where systemd takes no pidfd). What the child started in the meantime stays in Contour's unit. A refusal is not asked again, and neither is a child released while there is no systemd user instance at all: that is a configuration, not an outage, so its children run unplaced, quietly, with nothing kept to ask again.
    • NoPlacement (other platforms, Flatpak, builds without systemd) releases at once.

    What became of each child is told through an injected PlacementReporter, which Contour logs. Every child released unplaced for a fault is logged where a user sees it, with its pid and why -- each one, not only the first -- and so is its late placement.

    Before parking, the child also sets the oom_score_adj its placement supplies -- Contour's own plus 100 -- so in a global out-of-memory the kernel picks a session's process before Contour.

    The programs a session starts outside its terminal go through the same placement: the opener of a local file a link names (xdg-open), the viewer OpenCommandOutput hands a command's output to, the second Contour that follows a link to an executable file or opens one in $EDITOR, and the one spawn_new_process starts. ExternalLauncher starts each through vtpty::startDetached(), which spawns the trampoline, and the trampoline forks the program once -- the program is not Contour's child, and outlives it -- and parks the program's process on a gate exactly as Process::start() parks a shell. ContourGuiApp hands the sessions' factory and the launcher one placement. Windows starts them through QProcess, having no placement. The daemon contour client spawns, and the one contour daemon --background starts, go through startDetached() and a placement too: the daemon holds every hosted session's scrollback, and must live in neither the client's unit nor the scope of the tab it was typed into. --background's placement lasts only as long as the command does, which returns once the daemon accepts: a daemon deferred there because systemd fell silent is never placed late, and stays where it was started.

    What can still end up in Contour's unit -- a child released unplaced, what a late-placed one started before, and the shells the status line's Command segments run (CommandCapture, posix_spawn: one short run per refresh, bounded by a timeout and killed as a process group; a transient scope per run would churn systemd units every few seconds, per tab) -- no longer takes Contour down either: the Linux packages install systemd drop-ins setting OOMPolicy=continue on the unit a desktop launches Contour as (Contour cannot change its own running unit's OOMPolicy over the bus, so it is configured instead). Under <prefix>/lib/systemd/user/: app-org.contourterminal.Contour@.service.d/ for KDE Plasma's launcher (measured: KIO names it app-org.contourterminal.Contour@<random>.service) and XDG autostart, and …-.scope.d/ for the launchers that start scopes -- app-org.contourterminal.Contour- (KDE's scope launcher), app-gnome-org.contourterminal.Contour- (GNOME Shell), app-glib-org.contourterminal.Contour- (GLib). A drop-in applies to the next unit the desktop creates, and to a running one at the next systemctl --user daemon-reload. Services take OOMPolicy= since systemd 243, scopes only since 253: an older systemd (Ubuntu 22.04's 249, Debian 12's 252) ignores the three scope drop-ins, with an "Unknown key name 'OOMPolicy' in section 'Scope'" warning per launch, and a desktop that launches Contour into a scope there leaves it unprotected. An install to a prefix systemd does not search -- ~/.local, whose lib/systemd/user is not on the user search path -- installs drop-ins that have no effect.

    The spawn trampoline

    Contour is multithreaded, and fork() from a multithreaded process is only safe if no other thread holds a lock that the child, or an at-fork handler, then needs. That is a property of every library loaded, not of Contour's code. #2181 was the instance that bit: on macOS the attach worker forked the on-demand daemon while the main thread was inside QApplication's constructor, in setlocale(); Apple's libc takes the locale and malloc locks in opposite orders in its at-fork handler and in setlocale(), and the two threads deadlocked. Holding the spawn back until QApplication existed removed that race, not the class. So no first-party code forks from a threaded process any more: every child is started by posix_spawn of Contour's own executable in a hidden trampoline mode (vtpty/SpawnTrampoline.hpp). The trampoline is a fresh, single-threaded process, so everything between "spawned" and exec -- the placement gate, setsid, the controlling terminal, the working directory, the environment, the login-shell fallback -- runs without any lock it could trip over. It is the same work that used to run between fork() and exec(), moved after an exec instead of before one.

    The gate that held the daemon's spawn back did a second job, which outlived it: it kept the spawn -- and the service lookup before it, systemctl --user show or launchctl, and the service's start -- from racing the main thread's edits of the process environment. posix_spawn reads environ as surely as fork copied it, and the GUI changes its environment during boot -- it takes the GPU fallback request out of it, sets the OpenGL GPU selection and empties Qt Multimedia's hardware-probe variables, and QApplication's constructor unsets DESKTOP_STARTUP_ID (and may consume XDG_ACTIVATION_TOKEN). So terminalGuiAction() snapshots the environment first, on the main thread, before establishHosting() starts the attach's threads and before any of those edits, as the one a daemon it spawns and every service command it runs on the attach's worker runs under (vthost::daemonEnvironment()). The edits then run where they always did, beside the QApplication, so that enumerating the GPUs does not delay the attach. What they remove is taken out of the snapshot by name instead: the GPU fallback request and, on Linux, a parent Contour's GPU choice with its marker (display::bootRemovedGpuVariables()), and the two activation tokens, which belong to the client's first window. What they set -- the variables Contour sets for its own rendering, which local shells do not inherit either -- only ever fills what is unset, so the snapshot never holds it. The daemon thereby sees exactly what a snapshot taken after the edits, less those variables, would hold. For the daemon the snapshot travels as DetachedCommand::environment, and with it the trampoline is spawned under that environment too (TrampolineEnvironment::Program); the service commands go through vthost::makeNativeCommandRunner(environment), which looks the program up on the snapshot's PATH and posix_spawns it with the snapshot as its environment. Neither hands the live environ to a spawn, nor searches the live PATH.

    How it works

    • The marker. The parent runs the executable with argv[1] equal to --vtpty-spawn-trampoline=<version> (SpawnTrampolineMarker; the version is SpawnTrampolineProtocolVersion, 1 today). Every main() that can reach a spawn site -- Contour's, the test mains and the tools -- calls vtpty::runSpawnTrampolineIfRequested() as its first statement; on a marker it performs the trampoline and never returns, otherwise it returns and the program starts as usual. A binary that reaches a spawn site without the call would run its own main with the marker as an argument, so the call is the first line of every main(). On Linux the trampoline names itself contour-spawn (PR_SET_NAME), so ps and the OOM killer's report do not call it exe, after the /proc/self/exe it was spawned from; a test checks that it parks with one thread.
    • The spec. What the child is to become -- program, arguments, environment, working directory, lookup rule (exact path or PATH search), whether to take the PTY as controlling terminal, whether to configure the terminal settings, where an exec failure is reported (SpawnSpec) -- is serialized by the parent and read by the trampoline from file descriptor 3. A descriptor, not argv: an environment block can exceed Linux's 128 KiB limit for one argument. The trampoline itself runs under the parent's environment, so the dynamic loader finds Contour's libraries exactly as it did for the parent (LD_LIBRARY_PATH, DYLD_*) whatever a session's configured environment does to those; the child's environment travels in the spec and is installed right before exec. The exception is a caller that must not read the live environment -- the daemon's spawn, above -- whose snapshot, the parent's environment less a few names, is the trampoline's as well as the program's (TrampolineEnvironment::Program).
    • The slots. Descriptors the trampoline inherits sit at fixed numbers, set up with posix_spawn_file_actions_adddup2, from 4 up: 4 Gate (the placement gate), 5 Settle (the byte that says the terminal is taken on), 6 Terminal (the PTY slave), 7 FastPipe (the stdout fast pipe), 8 Input and 9 Output (the stdin and stdout of a detached program). A spec lists the slots it was given (TrampolineSlots).
    • The modes. A spec is the fields every mode shares plus a std::variant of the mode's own (TerminalLaunch, DetachedLaunch), whose index is the mode byte on the wire: a detached spec cannot carry a terminal-only field. Terminal is a session shell or the tmux client: place, take the PTY on, chdir, install the environment, exec, and on failure the diagnostics and fallback ladder the child always had, written to the terminal -- the fallback's text derived from its argv in the trampoline. Detached is a program started outside any terminal: the trampoline forks once -- safe, being single-threaded -- the intermediate process reports the program's pid (or -errno) over the gate and exits, the parent reaps it and places the program, which parks, sets its stdio, and execs. The program stays reparented to init, as before. Opening the PTY master stays in the parent, in vtpty: UnixPty hands its slave and fast-pipe writer over through Pty::spawnDescriptors(), and spawnOnNewTerminal() opens a fresh one for the tmux client.
    • One entry owns the protocol. vtpty::spawnPlaced() makes the gate, gives the spec the placement's oom_score_adj, spawns the trampoline, and hands the parked program to ProcessPlacement::placeThenRelease -- in Detached mode after reading its pid off the gate. Process::start(), startDetached() and spawnControlMode() (through spawnOnNewTerminal()) only build their spec and the descriptors beside the gate; the tmux client thereby gets the placement's OOM score adjustment like every other placed child.
    • Placement is unchanged. posix_spawn returns the pid that exec keeps, so ProcessPlacement::placeThenRelease places the trampoline process and, with it, the program it becomes; the program still starts only after the release byte.

    Finding the executable

    The parent spawns the running image, resolved by a stateless function:

    • Linux: the literal path /proc/self/exe. posix_spawn resolves it in the child, which still shares the parent's image, so it names the running file even after a package upgrade replaced or deleted it on disk.
    • macOS: _NSGetExecutablePath(), made absolute. The file at that path can be a newer version after an app update; the version marker is what keeps that safe.
    • FreeBSD and NetBSD: sysctl KERN_PROC_PATHNAME (CTL_KERN, KERN_PROC, KERN_PROC_PATHNAME, -1 and CTL_KERN, KERN_PROC_ARGS, -1, KERN_PROC_PATHNAME).

    Linux therefore requires /proc: without it there is no /proc/self/exe to spawn, and selfExecutablePath() says so (SelfExecutableError::NoProcFileSystem) rather than leave posix_spawn's ENOENT to explain it. OpenBSD has no way to name the running executable at all; every spawn fails there, with an error that says as much (SelfExecutableError::NoWayToName), as on any platform the list above does not name.

    On macOS the path is vtpty::currentExecutablePath() -- the resolved path vthost asks for too; on FreeBSD and NetBSD the sysctl is selfExecutablePath()'s own, as currentExecutablePath() answers not_supported there, keeping off what is built on it (the daemon's own images, relocation, bundled fonts) until it is brought up on those systems. Either way it is looked up once and cached (selfExecutablePath(), ExecutablePath.hpp).

    The version marker

    Parent and trampoline are the same binary except across an in-place update, when a still-running old Contour spawns the new file. The trampoline reads the version first; one it does not understand ends with a distinct status and a diagnostic on its stderr, which is the parent's. What the parent then surfaces depends on the mode: spawnPlaced(), for startDetached(), reaps the trampoline and returns a spawn error (protocol_not_supported, or bad_message for an unreadable spec). Process::start() does not look at the exit status of a session's trampoline: the diagnostic appears on the parent's stderr and the session sees its child exit with that status. Where the Terminal slot holds a terminal, the trampoline writes the diagnostic there as well, with \r\n line ends, so the tab says that Contour was updated while running and must be restarted instead of just closing. The slot is asked whether it is a terminal (isatty), not read from the spec, which is what may have failed to arrive; a parent of another version that put its terminal on another number goes without the tab's copy. Either way an old GUI fails to open new shells until it is restarted, rather than misreading a newer spec. Changing the spec's layout means bumping SpawnTrampolineProtocolVersion.

    Cost

    One extra exec of the Qt-linked executable per spawn: about 25-29 ms on a release build, measured, and accepted for a design with one binary and no helper to install.

    Audit: what still forks

    scripts/check-no-threaded-fork.py (CTest label lint) fails on a fork(, vfork( or forkpty( call anywhere in src/ outside the files below. Test code (*_test.cpp, src/*/test/) is exempt.

    Where Why it is outside the rule
    src/vtpty/SpawnTrampoline_unix.cpp The single-threaded trampoline: the Detached mode's one fork.
    src/crispy/StackTrace.cpp Forks addr2line on the crash and debug path, where the process is already going down.

    Not covered by the gate, because they are not first-party calls: QProcess::startDetached in contour/platform/QtExternalLauncher.cpp and contour/ContourGuiApp.cpp is Qt's own spawning, and Qt owns its safety. CommandCapture already used posix_spawn. Everything else that starts a process -- vtpty::Process, vtpty::startDetached(), spawnControlMode() -- goes through the trampoline.

    Invariants worth not breaking

    • Every path releases the child. Release is ParkedChild's destructor: an exception, a refusal, a timeout or shutdown cannot leave a shell parked.
    • Release is a byte sent with MSG_NOSIGNAL. Contour does not ignore SIGPIPE, and a child killed while parked must not take Contour with it. A byte, not end-of-file, because a sibling forked meanwhile inherits the gate's parent end.
    • End-of-file is no release for a detached program. awaitGateRelease() says whether the byte came. A detached program whose gate closes without it exits 127 unrun: that is spawnPlaced() giving up on a program whose pid never reached it, which its caller has been told failed to start. A session's shell still runs on end-of-file -- every path hands its trampoline to a ParkedChild, so only a parent gone before that closes its gate silently, taking the terminal's master with it.
    • The child waits on the gate before anything else. In the trampoline -- a fresh, single-threaded, exec'd process -- that is its first act after reading the spec, so nothing of the program runs before the placement; no async-signal-safe restriction applies to it any more.
    • placeThenRelease never blocks and never throws: Process::start() runs on the GUI thread and reports failures as values. One worker thread owns the sd-bus connection, and starts with the first session, with every signal blocked: the daemon waits for SIGTERM with sigwait().
    • A child that exited while queued is not asked about. Its pid may name another process by then; the pidfd says whether it is gone.
    • Each request listens for JobRemoved only while it lasts, through a match removed afterwards, and picks its own unit's job out; nothing queues up on the connection between spawns. The match must not name the unit: sd-bus matches argN only up to the first argument that is not a string, and JobRemoved begins with the job's number, so an arg2= match is routed to Contour by the broker and then never dispatched -- every request would time out although systemd placed the child.
    • Nothing thrown on the worker ends it, or Contour. Each child's placement is caught: the child is let go, the failure is logged, and a deferred child it concerned is not asked about again.
    • A wedged bus costs one deadline (1 s), not one per tab: the breaker skips requests for 30 s, then lets one trial request decide. Late placements run on the worker, a queued child before them, and one of them may be that trial; a tab never waits for more than one deadline per cooldown.
    • A deferred child is placed late only while its pidfd says it lives. One that exited is let go -- its pid may name another process by then -- and one without a pidfd is never kept. A pidfd is read as exited once it becomes readable, which a zombie's already is; signal 0 would still reach the zombie. Where systemd takes no pidfd (before 253), the late request names the pid, checked alive just before: a child that exits, is reaped and has its pid reused within that moment would have the unrelated process moved into the scope instead -- harmless, and not guarded further.
    • A late answer is still an answer. When a request runs into its deadline, the kernel is asked where the child runs (/proc/<pid>/cgroup, through an injected reader). A child already in the scope it asked for was placed. The request still waited out its deadline, though, so the breaker counts it as the silence it was, and it is told where a user sees it: answers that go astray for good -- as every one did while the JobRemoved match named the unit -- cost one deadline per cooldown, like a wedged bus, and do not go unnoticed. The price is latency: each late trial whose answer goes unheard as well holds requests off again, so deferred children are then placed one per cooldown -- after a restore of ten tabs, the last stays in Contour's unit for some five minutes. Placing them all in one pass would make the next new tab wait one deadline per deferred child.

    Testing

    vtpty_test "[placement]" covers the gate, the breaker and the worker through a fake ScopeBus. vtpty_session_oom_isolation (CTest label systemd) proves the requirement under a real user manager: a driver running as a unit with OOMPolicy=stop must end in oom-kill without placement and in success with it -- for a hog on a terminal, and for one started detached, as the launcher starts programs. It also places a first and a later child through fresh placements and requires systemd's answer to each to be heard -- systemd moves the child whether or not Contour hears it, so the hog's cgroup alone cannot tell. CI runs it under a lingering user session and fails if it skipped.
