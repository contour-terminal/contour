    Daemon mode

    Contour has always multiplexed — tabs and split panes, in one process. Daemon mode moves that ownership OUT of the window: a Qt-free daemon process owns the sessions and their layout, and thin clients connect over sockets, so the sessions outlive any client showing them. Two protocol families are served, and the same code also speaks the client side of both:

    • tmux control mode — external tmux-aware tooling (iTerm2-style clients, scripts) drives Contour's tabs and panes over the tmux 3.7b line protocol.
    • the native cells+deltas protocol — the server emulates, the client renders: per-line grid deltas addressed by stable row ids (wezterm's model).

    The module stack, bottom-up: core-cpp's core::async (C++23 coroutine primitives) → core::net (reactor EventLoop, sockets, buffered readers, write queues, TLS), both from the verbatim copy in vendor/core-cpp → src/vthost (the daemon, both protocol servers, and both client engines). The GUI may depend on vthost, never the reverse.

    One session, two taps

    A hosted session is {Pty, vtbackend::Terminal} owned by the daemon's SessionHost, pumped by a dedicated blocking-read thread exactly like the GUI's TerminalSession::mainLoop. Everything else — sockets, protocol state, the vtworkspace::SessionModel — is confined to one reactor thread; the pump threads marshal onto it via EventLoop::post().

    Each session's output is observable at two points:

    • the byte tap (TappingPty, a vtpty::Pty decorator): raw PTY bytes before the parser consumed them. This feeds tmux control mode's %output, which is byte-exact — the attached client emulates. Sixel/iTerm2/Kitty image bytes, OSC 66 and OSC 8 pass through untouched.
    • the cell tap (Grid::forEachLineChangedSince): per-line deltas after parsing. This feeds the native protocol — the client runs no parser.

    The pump loop flushes the terminal's queued replies (DA1, DSR, OSC color queries) back into the PTY after every processed batch. This is the daemon-side stand-in for the GUI's screenUpdated → flushInput hop; without it an interactive shell blocks in its startup terminal probes forever.

    tmux control mode (pinned: tmux 3.7b)

    The server (vthost/tmux/ControlSession) speaks the line protocol exactly as tmux 3.7b does — the installed oracle and the reference tree agree, and the layout codec's conformance tests drive real tmux select-layout:

    • guarded command responses %begin/%end/%error <time> <number> <flags>, the same triple on all three lines, flags bit 0 = client-originated;
    • %output escaping only bytes < 0x20 and backslash as exactly three octal digits (0x7F and ≥ 0x80 pass raw);
    • tmux's dual-queue ordering: a notification never lands inside an output block and never before output queued ahead of it;
    • pause/continue flow control with tmux's byte budget (high − buffered) / panes / 3, floored at 32; refresh-client -f pause-after=N switches emission to %extended-output %N <age-ms> : …;
    • layout strings with the rotate-add checksum; ingest collapses tmux's n-ary containers into right-leaning binary chains (round-trips compare trees, not strings);
    • refresh-client -C resizes within tmux's [1, 10000] bounds; the host then reprojects every pane's PTY size through vtworkspace::layoutInCells, so advertised layouts and actual shell dimensions never drift.

    The client side (tmux/ControlModeParser + tmux/TmuxGateway + tmux/TmuxClientModel) attaches to a real tmux -C (or to this project's own daemon — the loopback tests validate both halves against each other): recovery mode until the opening guard, FIFO command correlation, and a per-pane replay vtbackend::Terminal fed by the raw %output stream. History arrives once per pane via capture-pane -peqJ.

    Inherited limitation: tmux serializes only text and SGR in capture-pane — no images. A client attaching after an image was drawn cannot recover it from replay; images work while attached (live %output carries the bytes and the replay terminal parses them natively). Mitigation, if ever, goes through the native protocol — never through capture-pane.

    The native protocol (cells + deltas)

    The wire format (vthost/proto/) is wezterm's codec shape without the dependencies: a frame is varint taggedLength, varint serial, varint ident, payload, where the tagged length's low bit is a reserved compression flag (never set, always rejected — compression can arrive later without a version break). serial == 0 marks unsolicited server pushes. Unknown idents decode to Invalid{ident} — data, not an error — so newer peers keep talking. A ClientHello/ServerHello version handshake precedes everything. An accepted ServerHello also names the machine the daemon runs on, once for the connection: every command block's locality was judged against that machine, so the client decides whether it is its own before it mirrors a single session, and every mirror it builds keeps that verdict. A refused ServerHello names nothing.

    The machine id never travels as /etc/machine-id holds it, which machine-id(5) asks to keep confidential, but derived for Contour the way sd_id128_get_machine_app_specific(3) derives one (vthost::appSpecificMachineId) — the daemon's in the ServerHello, and every OSC 3008 context's machineid= alike (vthost::toWireContext); the client derives its own the same way to compare. On a systemd machine, systemd-id128 machine-id --app-specific=71621e7c11854bdbb34c6eddd2c15d97 prints the id a daemon there states.

    A mirror binds the verdict into its terminal as the terminal's replica role (vtbackend::Terminal::bindReplica): a replica of another machine's terminal holds every directory its application reports — a command block's, an OSC 3008 context's, the OSC 7 one — as foreign, showing it but never opening or spawning into it.

    Two limits ride here as well, both applying in BOTH directions: MaxFrameSize bounds a declared payload, and MaxGridExtent bounds an announced or proposed grid — an announced one because the client sizes a repaint buffer from it. Integral fields are decoded with a range check rather than a narrowing cast, so an out-of-range value is a MalformedPdu instead of a plausible small one.

    Version negotiation

    The handshake negotiates: each hello states the range of protocol versions its end speaks, and the daemon agrees on the highest one both ranges contain (HandshakePolicy::versions, by default proto::SupportedVersions, today { 4, 4 }), along with the capabilities both ends offer. The client takes any agreed version inside both ranges; the outcome is NativeSession::negotiated() on one end and NativeClient::negotiated() on the other. A peer whose range does not meet the daemon's is refused, and proto::describe phrases the refusal for whichever end reports it.

    The refusal discloses the daemon's supported range. It is the same ServerHello, byte for byte, whether the version or the token was wrong — for a peer from before negotiation (codecs 1 to 3) the version alone, for any other an agreed version of 0 beside the daemon's range, then the drop — so a peer probing it learns which versions the daemon speaks, but not whether its token was right. That discloses the daemon's whole supported range where a pre-negotiation daemon disclosed one u32; accepted, since the range is fixed per release and so public knowledge of it. The range is the diagnosis a user needs who upgraded and left an old daemon running: each end reports the other's (the daemon speaks protocol 3, from a release before version negotiation; this client speaks 4-4). When the two ranges overlap, the refusal was not about the version, and the text says so: wrong token or insufficient rights.

    The hello layouts. The diagnosis has to survive the revisions between the two ends, so both hellos lead with a u32, and every negotiating hello's is proto::NegotiatingHelloMarker (4). A hello leading with any other value is a pre-negotiation peer's, decoded no further than that version.

    PDU Layout
    ClientHello u32 4, one blob of varint min, varint max, varint count + varint idents, string token, optional session settings and whatever a later version appends, then one zero byte
    ServerHello (negotiating) u32 4, one blob of varint agreed, varint min, varint max, varint count + varint idents, string machineId, string hostname, string releaseVersion, varint count + varint followedWindows, varint daemonInstance and whatever a later version appends
    ServerHello (version alone) the u32 alone: the refusal a pre-negotiation client (0.7.0 on codec 1, 0.8.0 on codec 2, or codec 3) reads

    Each stays readable to contour 0.7.0, whose daemon decodes a hello whole before it checks the version and refuses a byte too many: it reads the ClientHello's blob as a token and the zero as "no session settings", and answers with its version. Codecs 2 and 3 consume everything after a version not their own. vthost/testing/ShippedCodec.hpp holds both hellos to 0.7.0's reader, and PreNegotiationCodec.hpp to those of codecs 2 and 3. The pre-negotiation revisions were:

    • 1: contour 0.7.0.
    • 2: command blocks (#1010) — each row's block id and birth time, the block records and their id epochs, the daemon's machine in the ServerHello, and engine operations.
    • 3: status-line extensions — a Delta's status rows name the display they are for, and the PermissionRequest and PermissionReply PDUs.

    A peer of any of them gets only the readable refusal; no old codec is kept for them.

    Capabilities gate new features; a version step is for a changed meaning. An optional feature is a proto::Capability, offered in the hello by the end that supports it and used only when both did (Negotiated::shared). Adding one is a row in proto::CapabilityTable:

    Capability Ident Name Gates
    ExtensionPermissions 1 extension-permissions PermissionRequest / PermissionReply: the daemon asks an extension's permission question only of a client with which it shares it; one that did not offer it is never asked, and the question waits for another client, as it does while none is attached
    ControlPermissions 11 control-permissions A PermissionRequest's appended control list (the control-API permissions an extension's manifest declares, granted with its commands): a question that asks for any is sent only to a client sharing it, whose prompt shows them; one that would prompt with the commands alone is not asked, and the question waits for another. So an older client is never asked about such an extension at all -- its commands stay ungranted there too, and the extension shows only its own "not granted yet" text until a client sharing the capability answers
    InputEcho 12 input-echo SessionInputEcho: the daemon tells a client sharing it what each session's terminal does with typed text, so the client locks a pane at a password prompt and turns its OS's Secure Keyboard Entry on. A client of an older daemon stays at Unknown: no lock, no secure input
    TabMerge 13 tab-merge MergeTabIntoSplit: the daemon grafts a whole tab, sessions and all, beside a pane of another tab. A client offers a drop-to-split only to a daemon sharing it; against an older one the tab is left to tear off into its own window, as before
    TabEditAcks 14 tab-edit-acks The daemon stamps each LayoutState it pushes with servedEdit, the serial of the last EditTab of that connection it had served; the client keeps its unserved activations in force over a push composed before them (vthost::client::PendingTabEdits). Against an older daemon, or for an older client, pushes come unstamped and a push in flight undoes a click until the echo, as before
    MoveNode 16 move-node MoveNode / MoveNodeRefused: the daemon moves a pane or a whole tab to an edge of a pane, onto a pane (a swap), into a window's tab well, or into a new window, with every session running throughout. A client offers a pane drag, and every drop that needs more than the older tab verbs, only to a daemon sharing it; against an older one the drop shows the "daemon is too old" refusal (see MoveNode)
    LayoutBatch 17 layout-batch LayoutBatchEnd: the daemon follows every push of LayoutStates one change made, across every window the connection follows, with one end marker, and a client reconciles a settled snapshot per batch instead of per frame. Without it a client decides at the end of each read, and a session a push dropped from one window may be in flight to another

    A capability's ident travels as a varint and unknown idents survive decoding, so a newer peer's offer costs an older one nothing. A protocol version step is reserved for a change to an existing PDU's meaning.

    PDU bodies are append-only. A body grows only by appending fields at its end; a decoder ignores the bytes after the fields it knows and gives a field missing at the end its default, so a peer older or newer by one appended field still reads the PDU. A field that is itself a growing record travels as a blob, so its own appended fields stay inside it. Both hellos' blobs follow the same rule: a new hello field goes at the end of the blob, gated by a capability. The catalog of PduType tags is kept contiguous; renumbering or retiring a tag changes existing PDUs' meaning, so it takes a version step. The two hellos keep 0.7.0's tags, as they are how two versions meet at all.

    Unsupported (tag 24) answers a PDU a peer does not know. After the handshake, a frame whose tag the receiver does not know is answered with Unsupported { refusedSerial, ident }, and the connection continues. Its receiver stops sending that tag for the rest of the connection (NativeSession::peerRefused(), NativeClient::peerRefused(), both kept by proto::UnsupportedTracker) and never answers an Unsupported with another. Before the handshake no PDU is answered with one: the daemon answers anything but a ClientHello with a version-alone ServerHello and ends the connection, as it did before negotiation, and the client ignores anything but the ServerHello — a session PDU arriving first is logged, not applied.

    The compatibility window. A release speaks at least the protocol versions of the previous two releases, counted from the first release that ships the range handshake. proto/ReleasedVersions.hpp holds the data: ReleasedProtocols, one row per release that shipped negotiation with the range it speaks, oldest first, always followed by the row { "unreleased", SupportedVersions } — the build under development, and until the first such release the only row (a static_assert pins it last and to SupportedVersions) — and LastReleaseBeforeNegotiation (0.8.0). compatibilityFloor() is the highest version of the row two before the newest — the older of this build's previous two releases — or of the oldest row while fewer exist, and Compatibility_test.cpp holds SupportedVersions.min at or below it: raising the floor of what this build speaks past that is a test failure. vthost/testing/RecordedTranscripts.hpp holds, per version, the bytes that version's client and daemon wrote for an attach — a ClientHello, an accepting ServerHello, a ResizeRequest and an Input — recorded once and never regenerated for a shipped version; every transcript of a version inside SupportedVersions must still be served: the daemon agrees on its version, answers no Unsupported, applies the resize and the input and keeps the connection open, and a client attaches to its ServerHello.

    Cutting a release: add a ReleasedProtocols row and record its transcripts. Insert { "<version>", <range> } just before the "unreleased" row, which stays last, and, when the release ships a version without a transcript, run vthost_test "[.dump]", which prints this build's attach PDUs in the header's layout, and append them to RecordedTranscripts.hpp. The [release] test enforces the step: it reads metainfo.xml (CONTOUR_METAINFO_PATH) and takes the newest <release> carrying a date= — undated type="development" entries and commented-out templates are not releases. While that is LastReleaseBeforeNegotiation, the only row may be "unreleased"; otherwise the row just before the trailing "unreleased" one must name it, and no other "unreleased" row may exist, or the test fails with add a ReleasedProtocols row for <N> and record its transcripts. /draft-release stamps the date, so the test turns red on the release branch exactly when the row is missing.

    Status-line extensions and the font

    A daemon-hosted session runs its status-line extensions in the daemon, which draws in no font: its clients do, each in its own. The native protocol carries no pixel sizes — ResizeRequest and the hellos are cells only — so the daemon cannot tell an extension the font a client draws its cells in. Its terminals are therefore never told any (Terminal::setStatusLineFontMetrics is a GUI-side call), their extensions receive no font-changed event, and state's font is all zeros, which the statusline world documents as unknown. A take-over's images are cut into cells of the extension's default size; a client draws whatever cell geometry it has.

    Why there is no CloseSession/Unfollow verb

    Session removal is covered from both ends without one, and the shape is worth stating because the absence looks like an oversight:

    • Client → daemon is ClosePane, authored where the intent is known — the manager's pane/tab-close paths, through SessionFactory::requestRemoteClose — never inferred from a destructor. A PTY dies on a pane close, a window close, an app quit and a lost connection alike, so contour::SessionEnd makes every teardown entry point state which it is. Getting that wrong is silent in both directions: authoring on a detach kills sessions the user meant to keep, and not authoring on a close leaves them running headless (the bug this replaced — NativeController:: unbind() was the only author, and nothing destroys a TerminalSession until app teardown, so no close was ever sent).
    • Daemon → client is the re-pushed LayoutState: every model change fans out through each connection's layout observer, and the client reconciles structurally rather than per session id (applyRemoteLayout's subtractive pass). A window whose last tab closed still reports, as an empty tab list, so removal is never signalled by silence.
    • Per-session server state is dropped on SessionStreamEvents::sessionClosed, which erases the session's follow state and pending-delta entry — a dead session cannot accumulate work.

    Adding the verb later is not a compatibility event, which is why it is not rushed in ahead of a release: it is a new PDU behind a capability (see Version negotiation), and an older peer that receives it anyway answers Unsupported. What genuinely costs a version step is changing an existing PDU's meaning.

    What a client syncs back

    A client rebuilds its windows from LayoutState, so anything it changes about a tab and does not tell the daemon is lost on the next attach, and never reaches another client. Two verbs carry it back: ResizeSplit for a divider (below), and EditTab for how a tab is presented — its active pane, its zoom, its title, its colour, and which tab of the window is active.

    EditTab (tag 28, gated on Capability::TabEdits; without it the daemon answers Unsupported) names a session and a TabEditKind, and vthost::applyTabEdit applies it through one table row per kind: ActivatePane → setActivePane; Zoom/Unzoom → activate the pane, then toggleActivePaneZoom only when the zoom differs; SetTitle/ClearTitle → setTabTitle/resetTabTitle; SetColor/ClearColor → setTabColor/resetTabColor as TabColorSource::User; ActivateTab → activateTab. Every row compares before it mutates, so a client re-asserting state the daemon already holds fires no model event and so costs no client a layout push; a change fans out as a fresh LayoutState to every client, the sender included. An edit naming an unknown session or kind is logged with describe(TabEditError) and answered with nothing.

    The daemon pushes a layout on every model change, so a push composed before it read a client's edit (a title a shell set in another pane, say) still shows what the edit changed, and would undo a click until the echo arrives. Under Capability::TabEditAcks the daemon notes each EditTab's serial before applying it, and stamps every push with it (LayoutState::servedEdit, an appended varint). The client lays the ActivatePane and ActivateTab edits a push has not seen over it, and forgets those it has: the push is then the daemon's word, another client's later change included.

    MergeTabIntoSplit (tag 35, gated on Capability::TabMerge; without it the daemon answers Unsupported) is what dropping a tab on the edge of a pane sends. It names the dragged tab by ALL of its sessions, the pane to split by its session, and a vtworkspace::SplitSide byte; both ends are sessions because tab and pane ids are minted per model. vthost::applyTabMerge reads the side (splitSideFrom, never a cast) and runs the same SessionModel::mergeTabIntoSplit an in-process window runs: the dragged tab's sessions move into the target tab, and none is spawned or closed, which is why neither SplitPane (it spawns a fresh session) nor ClosePane (it would kill the dragged ones) could carry it. The model's events fan out as a LayoutState push per event the merge fires (five today), each already showing the merged tree. A request is refused, and logged with describe(TabMergeError), for an unknown session or side, both sessions in one tab, two windows (CrossWindow), or a tab that no longer holds exactly the sessions named (StaleTab: another client merged into it meanwhile, so the request would drag along panes nobody dragged).

    A refusal is not silent: the daemon answers it with TabMergeRefused (tag 36, under the request's serial, to a client that negotiated TabMerge), carrying the TabMergeError as a byte, and the client tells its user in a toast (NativeClient's TabMergeRefusedHandler, NativeController::tabMergeRefused). A merge that succeeds is answered by the layout push alone.

    A client does not merge locally, since the next push would undo it: NativeController::requestRemoteTabMerge sends the verb and applyRemoteLayout grafts the tab when the push arrives (findNewMerge recognises a leaf beside a subtree that is exactly one other local tab's sessions). The merge stays within one window, because a layout is pushed and reconciled per window. NativeClient::mergeTabIntoSplit writes nothing unless the daemon shares TabMerge, and SessionFactory::tabMergeSupport() tells the window, so a tab dropped on a pane of such a daemon is not offered a split.

    MoveNode

    MoveNode (tag 37, gated on Capability::MoveNode; without it the daemon answers Unsupported) generalises MergeTabIntoSplit into the one verb behind every drag of a pane or a tab. Like it, it names both ends by session, never by pane or tab id, because ids are minted per model. Its fields:

    Field Meaning
    sourceKind a vtworkspace::MoveSourceKind byte: Pane (0) or Tab (1)
    sourceSessions a pane source: its one session. A tab source: every session of the tab as the client sees it, the first naming the tab
    targetKind a vtworkspace::MoveTargetKind byte: Edge (0), Swap (1), TabWell (2), NewWindow (3)
    targetSession Edge and Swap: the pane, by its session. TabWell: any session of the window whose tab strip receives it. NewWindow: 0
    side Edge only: a vtworkspace::SplitSide byte
    index TabWell only: the position among the window's tabs (clamped into range)

    vthost::applyMoveNode (vthost/NodeMove.*, pure over the model, so every refusal is table-tested without a socket) reads both ends, and only then runs the vtworkspace::SessionModel::moveNode an in-process window runs. Kinds and sides are read through std::to_underlying tables, never cast. No session is spawned or closed, and a move is applied completely or not at all: it is validated before the model is touched, and a refusal fires no event. On success the model fires its events, and every attached client is pushed the new layouts; there is no reply PDU. An emptied tab closes, an emptied window is removed, the moved pane's session takes focus in its new tab, and zoom is cleared on both tabs; a new split divides the target pane in half, a swap trades two places and each keeps its ratio.

    A NewWindow move is not made by the model alone. The daemon makes the window itself, through MoveWindowHooks (SessionHost::createEmptyWindow): the window gets its UUID binding like any other, and the requesting connection is recorded as its creator, so that the requester's follow scope adopts it (WindowClaim::Yours) and another attached GUI does not claim a window that is this client's own. The window then is the well of an ordinary tab-well move, and a refused move takes it away again (discardWindow) so a refusal leaves no empty window behind. A source that is already all of its window -- its only tab, or that tab's only pane -- is refused as the model's NoOp before any window is made (SessionModel::fillsItsWindow): moved, it would only tear its window down and build it again for every client. The same hook removes the window a move took its last tab out of, once every client was pushed it empty — its UUID and creator go with it, and when it was the host's primary window, the lowest-id window left takes that role.

    A refusal is answered with MoveNodeRefused (tag 38, under the request's serial, only to a client that negotiated MoveNode), carrying the reason as a byte, reason, and after it modelReason: the vtworkspace::MoveError byte when reason is Model, 0 otherwise:

    NodeMoveError Reason
    UnknownSession no pane hosts a session the request names: it closed, or never existed (a stale drag)
    UnknownKind a source or target kind this host does not know, or a pane source that does not name exactly one session
    UnknownSide an edge target's side this host does not know
    StaleTab the source tab no longer holds exactly the sessions the request named
    Model the model refused: vtworkspace::MoveError says why (UnknownSource, UnknownTarget, SelfTarget, TabIntoSwap, NoOp)

    A value this build does not know still reads as a refusal. The client logs the reason, and the GUI shows the user a toast (NativeController::moveRefused) whose text both bytes pick from a table (window::moveRefusedText): a stale source says the pane changed while it was dragged, a drop onto itself or one that changes nothing says nothing at all, and anything else -- a move the client could not even send among it -- says the daemon could not move the pane. A success is answered by the layout pushes alone.

    LayoutBatchEnd (tag 39, gated on Capability::LayoutBatch) closes a push. One move fires several model events, and to a client without the capability the daemon pushes each followed window's layout once per event, some of them between the move's halves (the window the pane left shows it gone before the window it entered shows it arrived). Under the capability each event only marks the window it is in, and the batch it opens is pushed once the frame that made the change has handed control back to the loop: each marked window this client follows, once, as the change left it -- a marked window the change removed goes out with no tab, so the client closes its own window for it -- and then one LayoutBatchEnd. The PTYs are resized as each event is fanned out, before that, for every client alike, so they have their sizes before the client sees the layout. Its field causeSerial is the serial of the MoveNode whose effects the batch completes, 0 when no request of this client caused it. A client therefore reconciles one settled snapshot per batch (NativeController::layoutsSettled): the layouts it holds when the end arrives are the state the change left, across every window, and a session that none of them names is gone, not in flight. The client that asked completes its move on the batch: the serials only grow per connection, so a batch ended by serial S completes every move it has in flight up to S (NativeController::takeCompletedMoves), including one that pushed nothing: the batch of a move is ended to the client that asked for it even when it follows none of the windows the move changed. A move whose window is never placed expires after five seconds instead of waiting for ever.

    Against a daemon without LayoutBatch, the client keeps the older park and settle path: a session a push dropped from every window is parked (NativeController::parkSession) rather than ended, and decided at the end of the read that brought the frame: if a later layout names it, its window takes over the same TerminalSession; if not, it is closed. That is correct, but it can only guess at the end of a push, which is why the batch marker exists.

    SetSplitOrientation (tag 40, gated on Capability::MoveNode, the same feature family; without it the daemon answers Unsupported) sets one split's axis. Its fields are anchorSession, a leaf inside the split -- the split is that leaf's parent -- and state, a raw vtworkspace::SplitState byte. The byte is carried, not judged: the daemon calls SessionModel::setSplitOrientation, which refuses one that is neither Horizontal nor Vertical, an unknown session and a single-pane tab, each as a logged no-op. A split already on that axis fires nothing. On success the model fires paneOrientationChanged, and every attached client is pushed the layout in the same batch machinery a move uses; there is no reply PDU. The GUI sends it for "Toggle Split Orientation" when the daemon serves MoveNode and does not flip locally, because the next layout push would revert a local flip; against an older daemon it keeps the local toggle.

    Coexistence with MergeTabIntoSplit. A daemon serves both. A client that shares MoveNode sends every drop as one; a client that does not, against a daemon that shares TabMerge, still merges a whole tab beside a pane of its own window with MergeTabIntoSplit, and reorders, moves and tears off tabs with the tab verbs. The GUI's move table (contour::window::LegacyMoveRoutes, which moveRouteOf consults) names exactly what a host older than MoveNode still does, and anything it does not name is refused with the "daemon is too old" note, so a drop is never half done. MergeTabIntoSplit stays for as long as such clients are supported.

    tmux control mode. A contour client --tmux window is a gateway, not a model the GUI can move into, so a drop there is refused on the client (MoveRefusal::Tmux). On the serving side, tmux::ControlSession, which mirrors the model to a tmux client, treats a move as the layout change it is: tabMovedToWindow raises %sessions-changed and a %layout-change for the tab, and paneSwapped the layout change alone.

    Persistence. WorkspacePersistence observes the model, and tabMovedToWindow is one of the events it takes as a SnapshotTrigger::LayoutChanged, so a move is saved with the next layout snapshot and a restored workspace has the arrangement the user left (see Workspace snapshots).

    Where a split ratio lives

    In the daemon's model, or the user loses it. A client rebuilds every tab from LayoutState on attach, so a divider the daemon never heard about comes back at the ratio the split was created with. Both client-side mutators — the QML divider drag and the ResizePane keybinding — converge on vtworkspace::ModelEvents::paneRatioChanged, and that one callback is where ResizeSplit is authored (TerminalSessionManager::paneRatioChanged → SessionFactory::reportSplitRatio).

    ResizePane is the near miss worth naming: it carries the CELLS one pane is drawn at, and SessionHost::applyPaneSize documents that the next re-projection recomputes those from the ratio and discards them. A grid is a consequence of a ratio, not a place to keep one.

    Two details the mechanism rests on:

    • The split is named by two of its leaves, not by a pane id — matching SplitPane/ClosePane/ ResizePane, all session-keyed. The server resolves their lowest common ancestor (vtworkspace::Pane::lowestCommonAncestor), which is the same split node in either tree. Any leaf from each side works, so neither end has to agree with the other on how to pick one.
    • Ratios are compared in WIRE units (proto::toWireRatio, 1/10000), on both ends. The daemon ignores a report that re-asserts the ratio it already holds — a client re-asserting its layout on attach would otherwise cost every attached client a re-projection and a fresh LayoutState — and the client's reconciler writes only when the quantized values differ. Comparing decoded doubles instead would see a difference on every push that no write can remove.

    applyRemoteLayout therefore has a third pass, after the additive and subtractive ones and on the settled tree, that re-flows an already-realized tab when another client moves a divider. It pairs each wire tab with the local tab that matches it leaf-for-leaf, so a tab caught mid-reconciliation is skipped rather than written onto.

    How a tab's presentation travels

    The same pairing carries a tab's presentation both ways, compared as one vthost::client::TabPresentation (active and zoomed pane by session, title, colour, and whether the tab is its window's active one). Outbound, the five model events that can change it (activePaneChanged, paneZoomChanged, tabTitleChanged, tabColorChanged, activeTabChanged) call SessionFactory::reportTabPresentation, which names the panes by their ptys, since only the factory knows what a pty is bound to; NativeController translates them to sessions and sends one EditTab per field tabEditsToReport finds different. It compares with the last LayoutState for the tab, or with what it reported since, until the next push of that window: a zoom also retitles a tab, and the second report must not send the zoom again. Inbound, applyRemoteLayout's last pass runs tabEditsToReport the other way round — what the daemon has that the local tab has not — and applies the edits to the local model through the daemon's own applyTabEdit, with the sessions translated, so the two ends cannot disagree on what an edit means. The colour compared and applied is the user's (TabColorSource::User), never the effective one: a profile's or an application's colour is the client's own business. Nothing echoes: the last pass runs inside the realizing bracket, and reportTabPresentation drops what arrives during it.

    Line PDUs carry the full per-cell renditional state (grapheme cluster extras, widths, OSC 66 scales and packed extras, hyperlink ids, colors, the 20 CellFlags bits) plus per-batch side tables: hyperlink id→URI (sent once per connection on first reference, immune to the server-side LRU evicting the id later) and image-covered cells. Image pixels are never inline: clients fetch by stable image id (FetchImage → ImageData/ImageGone), served from ImagePool's id→weak_ptr index — eviction stays refcount-driven.

    Full per sent cell, that is — a row does not send the trailing columns that already match its own fill, and a uniformly-filled row sends no cells at all. A shell line occupies a fraction of the grid's width, so across a scrollback that padding is the bulk of a snapshot, at ~24 bytes per unused column. This makes the fill a shared contract rather than a rendering detail: an absent column means a default cell wearing the row's fillForeground/fillBackground and otherwise SGR-reset (the fill carries neither an underline color nor flags, so a row whose fill has either has nothing to omit), and every client render path must paint that fill across the row before writing cells over it. A path that reconstructs the cells alone truncates every filled region at the last column that happened to be sent — which is why applyWireLine clears the row to fillAttrsOf(row) before writing any cell, and why the same function serves the page, the history and the host-writable status line.

    Actions that change hosted state

    A client's terminal is a mirror rebuilt from deltas, so an action that changes the engine's state — ClearToPrompt, ClearHistoryAndReset, SoftReset, WriteScreen — would change only the mirror if it ran there: the host's rows stay, every other client keeps them, and the next delta may undo the change. Such an action is performed where the session lives. The client sends PerformOperation, naming the session and a proto::EngineOperation; SessionHost::performOperation applies it to the hosted Terminal and announces a screen update, and every attached mirror follows through its deltas as it follows output.

    It is one verb carrying an enum, not one PDU per action, and both ends keep a table:

    • The client (contour/session/HostedOperation.hpp) maps each action to an operation, and each operation to where it runs on each kind of remote end. A session asks its SessionFactory where the operation runs: a local factory runs it here, NativeController sends it to the daemon, and the local handler then does nothing. With the connection gone the action reports no success and the user is told, rather than the request being dropped on the floor.
    • The host (SessionHost.cpp) maps each operation to what it does to the Terminal, and to the thread that does it. The loop thread performs the resets and the clear, under the terminal lock the host takes. A write is handed to the session's pump, which parses it between two reads as it parses the application's output, in order with the client's input: the loop thread neither sleeps in a smooth-scrolling (DECSCLM) linefeed nor writes a reply to a PTY. Like every parse, it writes what it sends only once it has let go of the terminal lock, which the loop takes to build every attached client's delta: a write the application leaves parked never holds it.

    The next such action is an enumerator, a client row and a host row. An operation the host does not know — from a newer client — decodes all the same and is refused and logged by the host, as an unknown PDU is. The PDU arrived with revision 2 of the codec.

    A vi mark is such an operation too, though no action asks for it. A mirror's terminal is a replica, so mm there changes no row (Terminal::toggleUserMark): it raises userMarkRequested, and the session sends SetUserMark or ClearUserMark naming the row. The row is the host's, and only the mirror can name it: ScreenMirror::hostRowOf counts from where the primary page stood, in the mirror's own row ids, when an update last wrote it, and answers with the host's stable id and the host grid's stable-id generation of then (Delta::stableIdGeneration). The host places the mark through Terminal::placeUserMark, which passes over a row named in a generation since gone, and the row comes back flagged to every client. A mark is therefore the session's: every client shows it, and the host's reflow carries it. A row the host no longer holds, or one asked for while the mirror's own reflow is ahead of the host's, has no name, and the mark is not sent.

    tmux tabs run the parser locally on %output, so their terminal is not a delta mirror, but it is not where the pane lives either. The table's tmux column says what happens there. SoftReset and WriteScreen change only that local terminal, as they do in a local tab. ClearHistoryAndReset also sends clear-history for the pane, as iTerm2's tmux integration clears a buffer. ClearToPrompt is refused with a notice: tmux has no command for it, and dropping rows locally would leave the server's pane — what a re-attach replays — as it was.

    Why the client does not render escape sequences

    A thin pane must be indistinguishable from a local one — same behaviour, same rendering — and for a while the client got there by re-serializing each delta into VT bytes and feeding them to the session's own parser. That was appealing: one mechanism, no new API, and every feature built on vtbackend worked because a real vtbackend was doing the work.

    It cannot reach parity, for a reason no amount of extra sequences fixes: the escape-sequence vocabulary cannot express everything a grid holds.

    • LineFlag::Wrapped has exactly one producer in the whole engine — a real autowrap, in Screen::crlfIfWrapPending. No sequence sets it. A mirror that cannot say "this row continues the one above" has no logical lines, so reflow on resize, double-click selection, search across a wrap and the shell's semantic marks all worked from wrap state it had invented.
    • Line::promptEndOffset() / commandEndOffset() have no spelling at all. The terminal takes them from wherever the cursor stood when the shell spoke OSC 133, and Line::reset() — which every row erase goes through — clears them, so even a re-emitted OSC 133 would need re-asserting after every repaint.
    • Reproducing the marks with real OSC 133 would additionally feed the client's CommandBlockStore command text and exit codes it does not have.
    • The underline STYLES had no distinct representation either, because the shared flag→SGR table held one integer per flag and could not spell 4:3.

    So the client writes the fields the wire names into the fields they name. That has no ceiling, and it is cheaper: an update no longer costs ~25 bytes of SGR per cell plus a full re-parse.

    What that obliges the populator to do by hand. Bypassing the parser means bypassing the bookkeeping Screen performs, so every write goes through the narrowest engine primitive that maintains it rather than at the arrays underneath — cells via writeCellToSoA (the trivial render fast-path flag, the grapheme-cluster pool, image-fragment replacement), scrolling via Screen::scrollUp (the cursor iterator, plus onBufferScrolled for the viewport, the Vi cursor and any live selection), the cursor via Screen::moveCursorTo, and the frame via Terminal::screenUpdated — called outside the terminal lock, exactly where Terminal::processInputOnce publishes a parsed chunk.

    Where the wire and the engine disagree, the sender wins: applyWireCell restores width and scale after those calls, because writeCellToSoA resets scale to 1 and appendCodepointToCluster re-measures the cluster. The authority on how many columns a cluster occupies is the terminal that ran the emulation, not the one displaying it.

    The parity oracle

    Parity is a claim about every cell and every line of two grids, which nobody can settle by reading code. vthost/testing/GridParity compares them field by field, and [parity]-tagged cases in client/ScreenMirror_test.cpp drive one content shape each through the real server + client + mirror loop.

    Three things make it trustworthy:

    • Both sides are read through the daemon's own toWireLine, so the comparator is exhaustive over the protocol's vocabulary by construction — and rows are expanded to full width first, so a blank row and a materialized row of identical appearance do not read as different.
    • Fields are compared from tables (LineFields, CellFields), so a field added to the wire is one row here rather than a chain of ifs that can silently omit it. Images are the exception, and the reason the tables are not the whole story: they travel in a side table beside the rows, so a comparator built only on wire rows is blind to them — hence describeImage, read off the storage.
    • Each probe states what the SERVER must be holding (serverLineFlags, serverHasCellFlag, serverHasImage). Two grids equally EMPTY of the thing under test pass trivially, and a probe that never engaged its feature looks exactly like one that proved parity for it.

    Comparisons resolve the page through Terminal::displayedPageIndex() — the page the daemon actually serializes. Not currentScreen() (the page VT output targets, which a decoupled display or an NP/PP flip makes a different page), not activeDisplay() (which follows DECSASD), and not isAlternateScreen() ? alternateScreen() : primaryScreen() (which reads the xterm alt page, where DEC pages 1..14 do not live).

    The resize probes carry the load-bearing assumption: reflow runs twice, once per grid, with nothing synchronizing them. They agree only because both grids were faithful copies and reflow is deterministic in (content, flags, old size, new size) — so that agreement is measured, in both directions, rather than argued.

    The send queue: what a bound may and may not conclude

    net::WriteQueue's byte bound exists to detect a peer that stopped draining, and three rules keep it from firing on anything else. All three were learned the hard way — the daemon used to disconnect perfectly healthy clients on a window resize, and later refused to let them attach at all.

    • The bound governs the backlog, never a single frame. A frame landing on an empty backlog is always accepted, however large. A full-grid snapshot of a deep scrollback is legitimately megabytes, and its size says nothing about the peer; refusing it made a session with enough history permanently unattachable, a cliff neither end could avoid. The in-flight frame is still counted as owed to the peer (queuedBytes()), just no longer governed by the bound (backlogBytes()) — it can no longer be superseded or refused.
    • A snapshot supersedes what it re-describes. Frames are tagged with their session, and pushing a snapshot drops that session's unwritten frames (dropTagged) instead of stacking on top of them. Without it a burst of resyncs — a window drag, or an attach immediately followed by the client asserting its area — queues whole grids until the bound trips, for frames the client's mirror would have discarded on arrival anyway.
    • A producer that can pace itself must, and a snapshot is split so it can. The first two rules are about what the queue concludes; this one is about what a producer may hand it. enqueue is non-suspending and the drain is spawned onto the loop — EventLoop::spawn queues a handle, it does not resume one — so a producer that enqueues a burst without suspending never lets the drain run, and the queue is never empty after its first frame. The lone-frame exemption then protects nothing, and the whole burst has to fit the bound at once. That is what made a daemon with two scrollback-heavy panes permanently unattachable: the attach walked every pane pushing a whole grid each, and the second one did not fit. Snapshots therefore go through NativeSession's streamer, which waitUntilBacklogBelows a piece's worth before each PDU and splits anything past a piece into a proto::SnapshotPart run. The watermark is deliberately a low-water mark. Pacing to bound − piece delivers the snapshot just as well, but does it by riding the backlog just under the bound for the whole run — leaving a single piece of headroom for every producer that cannot pace itself, and refusing the first one that needs more. The piece is sized to the bound — snapshotPieceBytes, a quarter of it capped at SnapshotChunkBytes, which the 4 MiB default keeps — so a run holds about half the bound at most. A piece of a fixed size under a smaller bound sat in the backlog already over it, and an increment or a bell enqueued behind it cost the connection.

    The same rule has a second shape in-tree, for a producer that cannot suspend: ControlOutput::pump reads queuedBytes() and spends a headroom-derived per-pane credit, re-arming a timer while work remains, rather than waiting. NativeSession's own debounce re-arm does the same. Suspend where you can, budget-and-re-arm where you cannot — one rule, two shapes.

    What the third rule does not cover, and what is still open: the burst-in-a-non-suspending-callback shape is unprotected in tmux::ControlSession's reply path (emitGuarded sinks one frame per captured row against a 256 KiB bound, bypassing the credit pacer its own %output path uses) and in tmux::TmuxGateway (sendKeys/sendRawInput chop a paste into many commands). Both can still refuse mid-burst and drop a healthy peer. The deeper fix for the whole class is to make the bound mean what its comment says — refuse only when over bound and the drain has made no progress for some interval — which would protect the producers that structurally cannot pace.

    The complement to the first two lives upstream: a resync is only pushed when a grid actually moved. SessionHost reports that (SizeChange) rather than letting callers assume a resize request changed something, because clients re-assert an unchanged client area on every attach, and each pane's grid is clamped before it is applied — so both "different request, same grid" and "same request, discard a per-pane refinement" are real cases.

    A client's input: paused, never refused

    The other direction has the opposite constraint. A client's Input is written to the session's PTY, and a PTY write parks once the application leaves its input unread, so the loop thread never writes it: SessionHost::writeInput queues it for the session's pump thread, which writes it between reads. That queue must not grow without bound while the application reads nothing, and it must not drop either, since a lost keystroke is a corrupted command line. It applies backpressure instead: once a session holds SessionHostConfig::inputWatermarks.high bytes of unwritten input, the connection whose Input filled it is read no further (pumpPdus's awaitReadRoom), and that client's writes park in its own transport; once the session holds no more than low, the connection is read again. Every other connection and every other session is served meanwhile, so the daemon holds about the high-water mark, one PDU and one read chunk for each such connection. WriteScreen's text shares the queue (HostedSession::deliverOnPump), since the pump parses it, so it backs up alike.

    Two costs follow. A paused connection is polled rather than woken, which is acceptable for a state that only an application ignoring its input causes. And a client that disconnects while paused is noticed only once the session drains.

    Stable row identity in the grid

    The delta source lives in vtbackend (added by this work, guarded by the usual terminal lock, one byte store per mutation on the hot paths):

    • every Line carries a dirty bit set by all mutating entry points, and copy/ move assignment dirties the destination row (margin scrolls move whole lines between rows);
    • Grid names physical rows by stable ids maintained exclusively inside the ring-rotation primitives: scrolling changes a row's LineOffset, never its id. The eviction floor is monotonic within a generation and names the oldest history row wherever a Grid operation returns. It is kept as its own member rather than derived from historyLineCount(), so that a step which grows the history before the base moves cannot re-validate ids the floor has already passed;
    • wholesale rebuilds (resize/reflow, history-limit change, reset) bump a generation instead; ids are only meaningful within one generation;
    • finalizeRevisions() stamps dirty lines with a batch seqno lazily — only when a consumer queries; an idle or daemon-less terminal pays nothing. forEachLineChangedSince(cursor, f) self-finalizes, reports rows whose revision passed the cursor, and answers ResyncRequired on a generation change — a resync is a forEachValidLine() snapshot, never a "changes since seqno 0" replay, because post-rebuild rows legitimately keep revision 0.

    Perf gate (measured, clang-release, Callgrind): total Ir +0.30 % against the pre-retrofit baseline (acceptance was < 0.5 %), writeTextToSoA and Screen::writeText byte-identical, wall-clock parity.

    Transport and clients

    NativeSession (server) pushes an attach snapshot (SessionState + a snapshot Delta per session), then deltas off the host's screen-updated signal. The first update after a client's input (its echo, once per input within a 50 ms window) and the first increment after a snapshot flush at once; everything else coalesces for 20 ms into one Delta (vthost/FlushPolicy.hpp). Deltas also carry the currently-SET DEC private modes of a single-sourced mirrored-mode table (vthost/MirroredModes.hpp: cursor keys, keypad, backarrow, bracketed paste, focus, cursor visibility) — everything a client needs to encode INPUT correctly; a pure mode flip pushes even when no cell changed. Output-side modes (autowrap, origin, margins) stay local by design: the server's emulation already applied them to the cells.

    Every mode in that table must be an INDEPENDENT boolean, because the client replays the set by applying its rows in order — so two rows writing one underlying value would let the later one overwrite the earlier one's answer. Input state that is not an independent boolean rides its own field instead, pull+diffed like every other live value: the Kitty keyboard flag stack's top (CSI = flags ; 1 u), xterm's modifyOtherKeys level (CSI > 4 ; level m), and the resolved mouse state — protocol, coordinate encoding and wheel mode.

    The mouse is the case that proves the rule rather than illustrating it. Nine DEC modes write only those three values (9/1000/1002/1003 the protocol, 1005/1006/1015/1016 the encoding, 1007 the wheel), so a mode SET cannot express which spelling won: replaying {1000 on, 1002 on, 1003 off} in table order ends with the protocol OFF, because resetting any protocol mode clears whichever is active — xterm's rule too (really_set_mousemode). The visible symptom was that the mouse was dead on exactly those clients whose mirror was built while an application was already tracking, which read as an attach-order bug and was really this. SessionState/Delta therefore carry mouseProtocol (as its DECSET number, 0 for none), mouseTransport and mouseWheelMode, and ScreenMirror writes them straight through Terminal::setMouseProtocol/setMouseTransport/ setMouseWheelMode — after the modes, since DECCKM rewrites the wheel mode on the alternate screen and enabling a protocol resets it.

    While fixing that, vtbackend gained the xterm rule it was missing for the four coordinate modes: they are one mutually-exclusive setting, so a reset is effective only against the matching mode (xterm charproc.c, srm_EXT_MODE_MOUSE). Contour treated them as four flags, which additionally made CSI ? 1005 l and CSI ? 1015 l enable their encodings — they ignored the set/reset bit outright.

    A snapshot must state live state outright, defaults included. Live fields (title, cursor shape, cwd, default colors, status display, the two input-encoding protocols) are pull+diffed against a per-connection FollowState; on a snapshot they travel in SessionState instead of a Delta changed-flag, and the server then records them as sent. A client replay that re-emits such a field only when it is non-default therefore drops any value that returned to its default inside a snapshot — permanently, because the server will not mention it again. That is not hypothetical: a shell popping its CSI u flags in the same batch as a child's alt-screen entry left clients CSI-u-encoding keys for an app that had stopped asking, so Ctrl+A reached tmux as literal CSI 97;5u text.

    The daemon is the authority for scrollback, so it must have some. A bare vtbackend::Settings leaves maxHistoryLineCount at LineCount(0), and with no history the daemon cannot merely fail to replay it — Grid::scrolledOutDepthSince clamps to zero, so rows that scrolled off between two deltas cannot be named, and a client mirrors them as blank scrollback. DaemonConfig therefore defaults it non-zero, and contour daemon --config/--profile derives the emulation half of its session settings from the same config::emulationSettings() table the GUI's session factory uses (a client auto-spawning a daemon forwards both flags). When a burst still outruns what the floor can name, pushDelta promotes it to a snapshot: rows the daemon can no longer name become an honest absence rather than fabricated blanks.

    The invariants live at the mechanism, not at the policy above it. vthost:: hostedSessionSettings (vthost/SessionSettings.hpp) normalizes any settings a hosted session is about to be built with, whatever produced them — the daemon's profile, a client's stated preference, or a bare vtbackend::Settings. SessionHost runs it in its constructor and again in seedSession, so no caller can open the defect back up. Two things it asserts: a zero scrollback becomes DefaultSessionHistoryLineCount (a small one is left alone — the default is a default, not a floor), and goodImageProtocol is forced on, because that knob is maturing toward non-configurable and daemon mode adopts the end state now. The latter is also why it is absent from the wire: carrying a setting about to disappear would buy one release of fidelity and cost a wire break to remove.

    Emulation is owned by the daemon; a session inherits the profile of the client that CREATED it. ClientHello optionally carries WireSessionSettings — the emulation half of the client's resolved profile (history depth, reported terminal identity, reflow, grapheme clustering, frozen modes, image registers, sixel scrolling; never the page size, which ResizeRequest negotiates). The daemon applies it over its own settings, validating every field, and hands the result to the sessions that connection creates: CreateTab, SplitPane, NewWindow, and the first session an attach to an empty daemon spawns. Sessions that already exist are never re-emulated, which is what makes two clients on different profiles conflict-free rather than a race — an application that already read DA1 cannot be told its terminal changed identity. A client whose configuration changed restates its preference with SessionSettingsChanged, which replaces what its ClientHello stated for the sessions it creates from then on; contour client resolves its profile again before every session it asks for, from the configuration the GUI holds in memory (as a local new tab does), and sends the restatement only when the result differs, so a tab opened after a configuration reload gets the reloaded profile. Both contour daemon and contour client resolve those settings through the one config::findNamedProfile lookup (emulationSettingsFor, resolvedSessionConfigFor), so a warm daemon and the client attaching to it cannot disagree about what a profile means.

    Transient session events — bell, desktop notification, OSC 52 clipboard write — are one PDU each (SessionBell, SessionNotify, SessionClipboard), projected for consumers as proto::SessionEventPdu. They were briefly a single PDU with a kind byte and two anonymous strings, which forced every payload into the union of all of them and left nothing but a comment saying which field meant what.

    client/NativeClient mirrors sessions into a RemoteScreen — plain data any frontend can render — and contour client is the GUI frontend on top of it. Sessions survive detach; a reattach replays history. The daemon serves the native protocol on <control-socket>-native.

    The stdio relay

    contour daemon --stdio is the remote end of an ssh attach (ssh <target> contour daemon --stdio): it reaches this user's daemon on <control-socket>-native, starting it through phase 2's DaemonStarter when none serves (a registered user service first, so a stopped service is started rather than an on-demand daemon beside it), and then copies bytes both ways between its standard input/output and that socket (vthost/StdioAttach.hpp, vthost/ByteStream.hpp).

    Before the protocol it writes exactly one line, the preamble (vthost/StdioPreamble.hpp):

    Line Meaning
    contour-stdio 1 ready\n The daemon is reached; the native protocol follows.
    contour-stdio 1 error: <message>\n It could not be; the message says why, on one line. The relay then exits.

    A client scans for that line, skipping up to 64 KiB of whatever came before it — a remote login shell that prints a banner or a motd on non-interactive logins is the classic reason binary protocols over ssh break. Nothing may follow the ready line before the client speaks: the native server reads a ClientHello before it writes anything, and the client has not sent one yet, so a byte after the ready line is not the protocol and the scanner reports it as such.

    The relay never parses a PDU. It is a pipe with a preamble, so a relay of one release serves any protocol version its daemon and the client negotiate (see Version negotiation); an old relay in front of a new daemon costs nothing.

    Logging must never reach stdout, which is the invariant the whole transport rests on: every byte on stdout belongs to the protocol. The log's default sink is stderr and --log-file names a file or stderr, but that is not left to convention: makeProcessStdioStream() takes a private copy of stdout for the relay and points stdout itself at stderr, so a stray std::cout — a log category constructed after logging was installed, which defaults to the console, or a library's diagnostic — goes to ssh's stderr channel instead of into a frame. contour daemon --stdio takes stdout over that way first, before it loads its configuration: the configuration names the socket, so it loads before logging is installed, and a warning it logs then goes to the default console sink. Only a refused option combination is reported earlier, while stdout is still untouched; any later failure (a configuration that does not load, an unknown --size-policy) goes to stderr and, as an error preamble, to the client (contour_e2e_stdio_relay pins both). Stdout is read and written raw (fds 0/1, or the GetStdHandle handles on Windows), never through the CRT's text-mode streams, which would turn every 0x0A into 0x0D 0x0A.

    The client→daemon direction runs on a detached thread: a blocking read of process stdin cannot be interrupted portably, and the process exits as soon as the daemon→client direction ends, which is the relay's end.

    The ssh side

    SshTransportFactory (vthost/SshTransport.hpp) is the client end: an ITransportFactory whose connect() spawns, through the injected IStdioSpawner, exactly

    ssh -T -o BatchMode=yes -o ConnectTimeout=10 -o ServerAliveInterval=15 -o ServerAliveCountMax=3 \
    [-p PORT] -- [USER@]HOST contour daemon --stdio
    Argument Why
    -T No remote pty: a pty would translate bytes (\n → \r\n) and echo them.
    -o BatchMode=yes Key and agent authentication only. Nothing may prompt: a GUI has no terminal to prompt on, and a prompt nobody answers is a hang.
    -o ConnectTimeout=10 A host that does not answer fails within ssh itself, before the transport's own bound.
    -o ServerAliveInterval=15, -o ServerAliveCountMax=3 A dead peer (sleep, Wi-Fi) is noticed in about 45 s, so ssh exits and the reconnect loop takes over.
    -- Ends ssh's options. parseHostUrl already refuses a user or host that begins with -, but the argv does not rely on it: a destination like -oProxyCommand=… can never be read as an option.
    REMOTE_COMMAND contour daemon --stdio, or the host's remote_command:, verbatim.

    From the spawn to the preamble the attempt is bounded by SshConnectTimeout (30 s). Bytes before the ready line are skipped and logged (vthost.client); the ready line hands out the child's socket as the Connection, with the ssh child as its lifetime, so the child is reaped only after the socket is closed. The token is empty: ssh authenticated the user, and the relay connects to the user's own AF_UNIX socket.

    When ssh ends before the preamble, what it wrote to stderr is classified by SshFailureRules, a table of needles matched in order (first match wins), with exit code 127 meaning "the remote shell found no contour". A new message ssh or a remote shell prints is a new row there, and its words a row of the message table in SshTransport.cpp. Each failure maps onto a TransportErrorKind, and that decides whether ClientSupervisor retries: only an unreachable host and an ssh that ended for no recognized reason are Unreachable (Transient). A refused login, an unknown or changed host key, a missing or too old remote Contour, a login shell that prints more than 64 KiB, and the relay's own error preamble are all Permanent: retrying cannot fix them, so the window ends with the message instead of looping. ssh never yields DaemonAbsent: the remote relay starts its daemon itself and reports a failed start as an error preamble (Refused).

    Every failure path ends the child before connect() returns, and every connect() spawns a fresh ssh: a dropped connection's child is reaped when its Connection goes, and the next attempt starts anew.

    The GUI seams (contour client, contour client --tmux)

    The display stack consumes a session exclusively through TerminalSession::terminal(), so a REMOTE session is an ordinary TerminalSession whose vtbackend::Terminal sits on a vtpty::ChannelPty — the blocking-read, sink-driven in-memory Pty (promoted from the GUI test fixture, so its semantics were already test-proven). Nothing in the display/render/input machinery learns the session is remote:

    • Input: every keystroke funnels through the one _pty->write() in Terminal::flushInput; the ChannelPty's write sink posts it onto the controller's reactor (native: NativeClient::sendInput; tmux: send-keys -H hex batches — the quoting-proof channel for encoded input).
    • Resize: Terminal::resizeScreen's _pty->resizeScreen() fires the ChannelPty's resize sink, which NativeController::reportPaneGeometry coalesces onto the GUI thread and flushGeometry turns into a COMPOSED ResizeRequest (the whole content area, solved back up the pane tree) plus a ResizePane per pane; the tmux path sends resize-pane -x -y. The client area is a report of what this client can display, not an instruction — @see "One grid, several clients" for how the daemon resolves one from all of them.
    • Output, native path: client/ScreenMirror populates the session's vtbackend::Terminal GRID directly from the delta stream — no bytes, no parser — so scrollback, selection and search work natively on mirrored content. History enters by scrolling rows through the page (real scrollback, no filler); hyperlink ids are translated against the connection's side table into the mirror's own store. vthost/GridWire's applyWireLine is the exact inverse of the toWireLine that produced the row, sitting beside it so the round trip cannot quietly lose a field. See "Why the client does not render escape sequences" below for what forced this. Because that history is the MIRROR's, a full replay must not erase it unless the server discarded its own (LocalHistory::Keep vs Discard): the mirror is routinely deeper than the daemon, so rebuilding from the server's remaining rows truncated the user's scrollback on every resize, page flip and resync — in practice, every time a full-screen app started or quit. A generation bump alone does not earn a discard, because a RESIZE bumps it: this terminal reflowed the same rows at the same moment, so its history is the reflowed truth. Only a first replay, a reset or history-limit change (a bump with the size unchanged), and a server-side clear (detected as the floor outrunning the viewport advance) discard. Two rules keep that decision honest. Neither the floor nor the generation may be compared across a page change: the 16 pages are distinct grids whose ids and generations advance independently, so a primary↔alternate flip was being judged on numbers from an unrelated id space — a spurious discard where they differed, and no rebuild at all where they collided. And Keep preserves history, it does not decline to have any: where the target page holds no local scrollback the replay streams the snapshot's rows in regardless, because there is no second copy to make. Without that, a client attaching while the session sat on the alternate screen never materialized the primary's pre-attach scrollback, though the wire had carried it. A vi mark comes back with its row. The mark is the host's (see Actions that change hosted state), so a row carries it on the wire like any other line flag, and the mirror writes the flags it is sent and keeps no mark of its own: a replay puts back exactly the marks the host holds, and a resize moves them as the host's reflow moved them. The retention bound is the client's own history.limit (RemoteScreen::historyKeep, stamped by NativeClient from the ClientHello's settings), not a constant: a hardcoded ceiling silently contradicted a user who had configured deeper scrollback — the daemon served the rows and the mirror dropped them. Absolute line numbers are the daemon's too. Every Delta carries the host grid's evictedRowCount beside stableFloor, so the row at the floor is number evictedRowCount + 1; it rides on every piece of a chunked snapshot with the rest of the scalars. After every replay and every delta the mirror hands its grid that count plus the distance from the floor to the server id of its own top row (Grid::adoptEvictedRowCount, a replica-only setter). Counting its own floor moves instead numbered from the oldest row the daemon still held at attach, never restarted on a daemon-side reset, and jumped by the whole local scrollback at every discarding replay, whose clearHistory() reads as an eviction. The field arrived with revision 2 of the codec.
    • Output, tmux path: the raw %output bytes ARE VT — TmuxClientModel's injectable PaneSink feeds them (buffering capture-pane replay until the local pty binds). The replay is capture-pane -peqJ -S -; -S - is what reaches past the visible page into the pane's history, and without it this direction replayed only the current screen while our own control-mode server was already answering -S - for tmux clients.

    Each controller (contour/remote/NativeController, contour/remote/TmuxController, sharing contour/remote/RemoteController) runs the Qt-free client engine on its own reactor thread (ReactorThread) and doubles as the app's SessionFactory: the manager's creation entry points ask canCreateSession() first, so a "+" click inside a mirror window cannot spawn a stray local shell. The app's factory is permanently a RoutingSessionFactory; attach mode switches the route, never the manager's reference. v1 mapping: one tab per daemon session; tmux windows become tabs and additional panes split the tab.

    One grid, several clients

    Several clients may attach to one daemon, and they share one grid per session — per-client server-side viewports were considered and not built (the F8 decision), since the alternative costs a viewport per follower in NativeSession plus a per-client delta cursor. Sharing one grid makes two questions unavoidable, and both used to be answered by accident.

    Which size is it? Not "whichever client reported last", which is a race rather than a policy: two differently-sized clients took turns resizing every application on the daemon. SessionHost keeps each attached client's reported area and resolves ONE authoritative area from all of them under vthost::ClientSizePolicy (--size-policy, default latest, mirroring tmux's window-size in both the values and the default). The resolution is a pure function of the reported set, which is what makes it settle: re-reporting the same areas in any order yields the same answer. smallest/largest combine per axis, because two clients can each be the wider and the shorter one. The registry is keyed by the client's stream subscription, so a detaching client's area stops counting — otherwise a client that is gone pins every application to its dimensions for the daemon's life. tmux's fourth value, manual, is deliberately absent: it needs a runtime verb to set the size with, and nothing here would drive one.

    Who hears about a change? Everyone, which is the half that was missing: the resync used to be issued by the connection that received the ResizeRequest, over its own follow map, so maximizing one window left every other client rendering the old grid — Terminal::resizeScreen raises no screen update, so nothing else would tell them either until that session next produced output. SessionHost::resizeLocked is the one place any grid moves, so it announces each move through SessionStreamEvents::sessionResized (with the terminal lock released, since observers take it to snapshot). Every path inherits it: a client-area re-projection, a per-pane refinement, a layout change. The connection that asked is no longer special.

    What a client that cannot show the grid does. A client LARGER than the grid letterboxes — the sub-cell remainder already renders as background padding, so the surplus simply is not drawn. A client SMALLER than it shows a window into the grid, positioned by vthost::client::viewportOrigin — tmux's tty_window_offset1 rule, ported as a pure function: centre the cursor horizontally once it is past the viewport, keep it on the last visible row vertically, clamp so the view never runs off the grid, and decide the two axes independently. ScreenMirror applies it on every update: local page row r shows the host's row origin.line + r, shifted left by origin.column, and the local cursor is the host's minus the origin. An origin that moves rewrites the whole page (the replay's page path); an unchanged one scrolls incrementally as before. Rows of the host's history are written unshifted, and the host's page rows above the window are not copied into local history. The mirror terminal adds the origin to every cell it reports in a mouse press, move or release (vtbackend::Terminal::setReportedCellOrigin), so a click lands on the cell the application drew there, not on the client's own cell.

    Which windows a client sees

    A grid is shared; a window need not be. A client states an attach intent in its ClientHello (proto::AttachIntent, honoured only when both ends share Capability::AttachIntent), and the daemon decides with the pure vthost::planAttach what that connection follows and what attaching creates:

    Intent Follows Creates
    AllWindows (no capability: every client before intents) every window, later ones included (FollowScope::Every) the first tab, on an empty daemon
    Launch, no other client attached every window with a tab the first tab, on an empty daemon
    Launch, another client attached a new window of its own that window
    NewWindow a new window of its own that window
    Windows the listed windows that exist (possibly none) nothing
    Resume the listed windows that survive, holding a tab; none surviving, as Launch as Launch when none survive

    "Another client" is SessionHost::connectedClients(): handshaken native Attach connections, counted after the plan (so a connection never counts against itself) and uncounted as the connection is destroyed. It is deliberately not the daemon's ClientCensus, which counts tmux and imsg clients too, for idle exit: a tmux gateway attached must not turn the first GUI's launch into a second window.

    The handshake runs negotiate → plan → create → ServerHello (whose followedWindows names the windows followed) → LayoutState per followed window → snapshots of their sessions. The plan runs after the hello's client area is applied, so whatever it spawns spawns at the client's size. Nothing reaches the peer before its ServerHello. From then on a connection is sent the layout, screens, resizes, bells, notifications and clipboard writes of followed windows only; a window that closes leaves the set.

    A window gains followers in two ways. One a connection creates (its NewWindow, or the window a launch made for it) is claimed for it in SessionHost before its first tab is announced, and that connection follows it. A window nobody claims — one the control API creates — is followed by the primary viewer, the connection whose Launch/Resume found no other client attached: contour new then appears in the GUI the user launched first, not in none. A claimed window stays claimed after its creator leaves, so a second GUI never inherits the first one's window; it waits for the next launch that takes every window. Each window joining a connection's set is sent its sessions' snapshots, since a quiet session would otherwise produce nothing to send.

    A client that loses its connection keeps its windows. vthost::client::ClientSupervisor opens every connection through an ITransportFactory (Transport.hpp), and after a loss reconnects with backoff (250 ms doubling to 5 s), each new connection stating Resume of the windows the lost one followed — or AllWindows again for a client that attached with it, so a reconnect never narrows its view. Window and session ids count from 1 in every run of a daemon, so the ids alone cannot tell a restarted daemon's window 1 from the one the client showed: the ServerHello states daemonInstance, drawn at random as the daemon starts, and a client that meets another instance takes every window it showed for lost. That is also why Resume does not take an empty window for a survivor — a restarted daemon's own primary window holds no tab yet. The GUI (contour::remote::NativeController) keeps every pane and pty while reconnecting, drops what is typed meanwhile rather than replaying it into whatever shell answers next, restarts each pane's mirror for the new connection's snapshots, and reports the lost windows (windowsLost) with the first window that came instead, so it can close them without closing the last one.

    A connection gone half-open (a laptop that changed networks, a host that vanished) produces no EOF, so the client does not wait for TCP to notice. client::LivenessTracker is a pure decision over time points the connection's loop clock supplies: after idleBeforeProbe (5 s) of daemon silence it asks for a Heartbeat and, after deadAfter (15 s) without any inbound frame, declares the connection lost, which hands over to the reconnect loop above. Any inbound frame counts as life, not only the echo. The probe is sent only to a daemon that shares Capability::Heartbeat; the ClientHello answer has its own handshakeDeadline (10 s) that applies to every daemon, so an old one that predates heartbeats is still not waited on forever.

    Control channel

    The daemon's control API (src/vtcontrol: windows, tabs, panes and command blocks, named by UUID, spoken in strict JSON) travels on the native connection, not on a listener of its own, so it inherits that endpoint's whole access rule and phase 5's --stdio relay. A caller connects with the Control role, which never views: no first session is spawned for it, it is sent no layout, no snapshot and no screen, it reports no client area and counts as no client. A connection's NativeSession::ConnectionPhase (AwaitingHello, Viewing, Controlling) is the one state the accepted hello decides; what was negotiated with it stays in negotiated().

    Three PDUs carry it, gated on Capability::ControlApi (control-api, 9):

    PDU Tag Direction Carries
    ControlRequest 30 client → daemon requestId, the method, the params JSON, the caller's $CONTOUR_PANE
    ControlReply 31 daemon → client the same serial and requestId, Ok with the reply JSON or Error with a ControlError
    ControlEvent 32 daemon → client a subscription id and one event's JSON

    A ControlRequest on a connection that does not share the capability, or on a Viewing one, is answered Unsupported for its serial and the connection stays open. Otherwise vtcontrol::dispatch serves it through NativeSessionServices::control — the daemon's control::ControlService, an embedded host's null object that answers every call unsupported — and the reply goes out once the call completes, at once or, for a wait, later. A Control connection keeps the status and stop verbs of the role (DaemonStatusRequest, StopDaemon), whether or not it shares the API, and is answered Unsupported for everything else.

    ControlService runs on the loop thread. What a session's parser raises — a finished or changed command block, a title, a working directory — the host posts to the loop as a SessionSignal before any observer hears of it, so subscriptions (EventHub) and waits (BlockWaiters) are never touched off the loop, and a terminal is only read under its lock.

    The reply bound. Pane text — a capture, a block's prompt and output — is cut to ControlServiceConfig::maxReplyBytes, a quarter of a connection's send-queue bound in the daemon, keeping its tail ("truncated":"head"), so one reply always fits beside a backlog and a pane with a huge scrollback never costs the connection. Every byte a pane printed is made valid UTF-8 and every control character escaped, so the JSON stays valid whatever the pane holds.

    Event backpressure. An event is not queued while the connection's backlog is past half its send-queue bound: a per-subscription counter grows instead, and the next event that fits is preceded by events.dropped { count }. A subscriber that stops reading therefore costs the daemon bounded memory and loses events, never the connection, and no viewer is affected. What a connection may hold is bounded too: ControlServiceConfig::maxSubscriptionsPerConnection (64) subscriptions and maxWaitsPerConnection (256) pending block.waits and pane.send waits; one more is answered limitReached and the connection stays open, a pane.send refused so typing nothing. Ending a subscription frees its place and its dropped-event counter (EventSink::subscriptionEnded); a connection's close frees its whole share. When a connection ends, its subscriptions and waits are dropped (ControlApi::sinkClosed) before it lets go of itself; an Attach connection's coming and going is published as client.attached/client.detached, beside SessionHost::noteClientAttached/noteClientDetached, so the events and connectedClients() agree.

    Grants. Every catalog row names a vtcontrol::Permission — read, screen, input or write — and a connection holds a vtcontrol::ControlGrants set, decided in the handshake with its token: HandshakePolicy::acceptedTokens lists the tokens an endpoint takes, each an AcceptedToken with its grants. The unix endpoint lists none, so any hello is taken with all four, the socket's owner check being the gate; a connection phase 5's --stdio relay carries arrives on that socket and holds all four too, ssh having authenticated it. The TCP endpoint lists --token/--token-file (everything) and the entries of --access-file (AccessFile.hpp), and a hello holds the grants of the first token it equals. vtcontrol::dispatch answers a row outside the grants forbidden (needs grant 'input') without calling the handler, a typed ControlReply and not a closed connection. A row may also name a requestGrant rule, a permission and the reason for it with a predicate on the decoded request, for what a request needs beyond the row's permission: tab.create and pane.split need input beside write when they name a command (CommandNeedsInput), since running a program is typing it. Each EventRow names a permission as well (block.finished needs screen, every other kind read): events.subscribe narrows the kinds it is given, or every kind, to those the grants allow, and refuses one that names only forbidden kinds. The role's own verbs are gated alike: DaemonStatusRequest needs read, StopDaemon write, and without it they are answered Unsupported, the daemon logging why. A narrow token is for Control connections only: an Attach hello whose token lacks any grant is answered with the very bytes of a wrong token (token lacks the grants an attach connection needs (has read,screen) in the daemon's log), before it is counted or spawns a session.

    Verified transports. ITransportFactory::peerTrust() says before connecting whether the peer is authenticated: Local for the unix socket, Verified for TLS against a pinned CA (--tls-ca) and for ssh, which checks the host key, and Unverified for TLS without a trust anchor, which encrypts but would hand the token to an active machine-in-the-middle. A control client refuses an Unverified transport before it connects; the interactive contour client keeps attaching over it.

    Program status

    A session's OSC 7501 records (vtbackend::ProgramStatusSet, at most 64) travel to viewers as one PDU, gated on Capability::ProgramStatus (program-status, 10):

    PDU Tag Direction Carries
    ProgramStatus 33 daemon → client a session id and its whole set, least recently updated first

    The set is state, not an event, so it is always sent whole and replaces what the mirror held; an empty set says every record is gone. A change raises ProgramStatusChangedSignal on the parser thread, which the host posts to the loop like every SessionSignal; a Viewing connection that shares the capability marks the session and sends its set at the next debounced flush, read under the terminal lock when it goes, so a program reporting in a loop costs one PDU per coalescing window. A snapshot sends the set before its rows whenever it is not empty. On the client the set is kept on the RemoteScreen, so a mirror bound later (or replayed after a reconnect) catches up from it, and ScreenMirror hands it to Terminal::replaceProgramStatus(). A record whose state the client does not know is dropped (control::fromWire); control/ProgramStatusConvert.hpp holds the one table per enum that bridges vtbackend's and vtcontrol's spellings. The control API reads the same set for PaneInfo.programStatus and publishes pane.programStatusChanged with the whole set and its reason, both only to a connection granted screen: a record names a program and what it is doing, as the command line block.finished keeps behind screen does.

    The text is never traced (ProgramStatus session=1 records=2).

    Input echo

    What a hosted session's terminal does with typed text (vtpty::InputEcho: Echoed, Raw, Hidden, or Unknown where the device cannot tell) travels to viewers so a client can lock a pane at a password prompt, gated on Capability::InputEcho (input-echo, 12):

    PDU Tag Direction Carries
    SessionInputEcho 34 daemon → client a session id and the echo state's value (vthost/InputEchoWire.hpp)

    The daemon reads it from the hosted PTY (UnixPty::inputEcho(), under the device's own lock, never the terminal's; TappingPty forwards it) on the loop thread at each flush, before the session's output, after input the client sent, and in a snapshot, and sends it only when it differs from what that connection was last told. A program may turn echo off after its prompt, or back on without printing, with no output or input to carry the change: so a connection that shares the capability also runs a coarse idle check (FlushPolicy::inputEchoCheck, 250 ms), on the loop's clock, that reads every followed session's echo when it is due and rides the flush machinery (a flush armed for the next check, superseded by any earlier one). The client stores the value on the pane's ChannelPty on the reactor thread, which then runs the pane's observer (vtpty::Pty::setInputEchoObserver); the session installs one that posts to its own thread and re-reads the echo there, so the lock appears without waiting for output. A value the client does not know reads as Unknown. tmux panes have no such field and stay Unknown.

    Who configures a daemon session

    The host's configuration owns what runs; the client's owns how it looks. A client names a profile — in its ClientHello (profileName), or on a spawning verb (CreateTab, SplitPane, NewWindow, whose name overrides the connection's for that one spawn) — and the daemon resolves the name in its own configuration through vthost::ProfileCatalog (contour::cli::ConfigProfileCatalog for contour daemon). The resolved profile supplies the session's settings and its whole shell: program, arguments, working directory and environment — the shell the in-process GUI spawns for that profile (config::resolvedSessionConfig), replacing the daemon's rather than layered over it, so no variable of the default profile reaches a session of another; only the daemon's own variables (hostedShellEnvironment) are added and win. Its escape_sandbox travels with it (ResolvedProfile::sandbox, through SessionHostConfig::profilePtys), as SessionFactory takes it from the session's own profile in-process: a contained profile is never run on the host because the default profile escapes. A spawn naming no profile resolves the default one the same way, keeping the emulation settings a client stated, if any. A layout pane's command/directory overlay that shell, and a startup layout's per-pane profile (else its tab's) is honoured the same way.

    A name the host does not know — a Windows laptop's pwsh profile against a Linux host — never refuses the session: the host's default profile (the daemon's --profile, else default_profile) runs, and the log says session N: profile 'pwsh' is unknown here; using 'main'. daemon.history_limit, when set, replaces every profile's history.limit on the host, since the daemon keeps the lines.

    It is gated twice. The daemon offers Capability::ProfileByName only when it has a catalog, and a connection that shares it and names a profile has its stated sessionSettings ignored. A client that does not share it keeps the older path, in which its stated emulation settings shape the sessions it creates and the daemon's configured shell runs.

    The catalog follows the configuration file while the daemon runs. contour daemon hands runDaemon a ConfigReloadHook whose poll (every 2 s, on the loop) compares the file's last-write time with the one last seen and, when it moved, loads it again into a fresh catalog (contour::cli::ConfigReloadPoller). SessionHost::replaceProfiles then serves new sessions from it, named or not, and gives every running session its profile's new scrollback limits under the terminal's lock; a running session's shell, environment and directory never change. A file that fails to load is logged and leaves the running configuration in force, and is not retried until it changes again.

    Socket conventions

    contour daemon/client default to $XDG_RUNTIME_DIR/contour/<label>, overridable per flag and $CONTOUR_MUX. The socket directory hardening mirrors tmux exactly: 0700 directory, owner check, refuse world-rwx (group is permitted — tmux's TMUX_SOCK_PERM == 7).

    The socket directory is made 0700 before the daemon opens its log: the log sink used to create it first with the default mode, after which the listener's owner-only check refused the bind (--background and every on-demand spawn into a fresh socket directory failed that way).

    vthost::daemonLogPath derives <socket>.log beside the socket, as the default destination for a daemon with no console to write to (--background, and anything contour daemon-service installs). It sits with nativeSocketPath/tmuxSocketPath because it is the same kind of fact: one place per label, derived rather than remembered.

    A path an installed daemon is given must be absolute, and resolved at install time. A registration outlives the shell that created it, and a service's %TEMP%/%USERNAME% need not be the interactive user's — so a socket left to be derived at start time resolves somewhere the user's own client never looks. daemonServiceCommandLine pins both the socket and the log file.

    Daemon lifetime

    Every shutdown carries a ShutdownCause (DaemonLifecycle.hpp), one row per trigger, and the single shutdown log line names it:

    ShutdownCause Trigger Log text
    Signal SIGINT/SIGTERM (POSIX) or a console-control event (Windows) signal received
    LastSessionClosed with --lifecycle=exit-with-last-session, the last hosted session going away the last hosted session closed
    Idle an ExitWhenIdle daemon with nothing to serve for its grace period idle
    StopRequested a Control connection's StopDaemon with reason User stop requested
    UpgradeRestart a Control connection's StopDaemon with reason UpgradeRestart restart for upgrade
    StopRequestedKeepingWorkspace a Control connection's StopDaemon with reason UserKeepingWorkspace stop requested, keeping the workspace

    All of them funnel into one ShutdownFunnel, which runs on the loop thread and runs once: a second request — a SIGTERM racing a StopDaemon — logs nothing and does nothing. The shutdown first calls DaemonConfig::beforeShutdown with the cause, while every listener still accepts and every session is alive, then closes every listener and unwinds the loop. A trigger off the loop thread (the signal watch, the console-control handler) or inside a connection's PDU handler (a StopDaemon) posts its request rather than running it there, for the reasons LastSessionWatcher posts.

    The signals come through DaemonConfig::shutdownSignals. Its default is the process's own — a sigwait thread on POSIX, the console-control handler on Windows — and a test that runs runDaemon in-process sets NoShutdownSignals, so the daemon neither takes the test process's signals nor sends the SIGTERM that unblocks its sigwait thread into it.

    runDaemon arms that watch before it constructs the SessionHost. The sigwait watch blocks SIGINT/SIGTERM on the calling thread only, and a thread inherits the mask it was started under: the host starts a pump thread for each session of a startup layout in its constructor, and a process-directed SIGTERM that reaches a thread not blocking it kills the daemon by the default action — before the listeners unlink their sockets, and as a failure a service manager restarts. Declared first, the watch is also destroyed last, after ~SessionHost has joined every pump thread, so the SIGTERM it sends itself after a StopDaemon has only its own thread to reach.

    The daemon itself is a DaemonRuntime, the DaemonControl behind every native endpoint. Besides an Attach connection — a terminal client, shown the sessions — a native connection may say in its ClientHello that it has the Control role: it asks the daemon about itself (DaemonStatusRequest, StopDaemon) and is sent nothing else. The daemon's ServerHello offers Capability::DaemonControl for it; an embedded host, whose null daemon control serves no such request, does not. A Control connection is no client: the ClientCensus counts Attach connections and every tmux control-mode and imsg connection, so a status probe never keeps an idle daemon alive.

    The lifecycle is --lifecycle (DaemonLifecycle): Persistent is the default, because a daemon started by hand or by a service exists precisely to outlive its sessions and still be there for the next client. --exit-with-last-session survives as an alias for ExitWhenEmpty. ensureDaemon starts the daemon it spawns on demand with ExitWhenIdle (no longer --exit-with-last-session): that one belongs to the clients that needed it, and "make sure a daemon exists" must not mean "leave one behind". The policy rides on the daemon, not on the spawning client.

    ExitWhenIdle is the IdleExitWatcher, which sits beside LastSessionWatcher (and, like it, answers mirrorsScreens() == false). It reads two things: the session count, from sessionClosed, and the client census. ClientCensus counts every connection that is a client — a native Attach connection, a tmux control-mode connection, an imsg connection — through countedHandler(...), which wraps each endpoint's handler; a Control connection is deliberately not wrapped. When both counts reach zero the watcher arms a timer for DefaultIdleExitGrace (10 s); anything that arrives re-arms it. The decision is re-checked at fire time, not only when the timer was armed: a client admitted, or a session created, in the very turn the deadline passed but before the loop ran the timer must keep the daemon, and a session creation fires no event the watcher hears. The re-arm is edge-driven — after a fire-time "busy" the watcher waits for the next clientCountChanged or sessionClosed.

    A service-managed daemon (contour daemon-service, the packaged unit) starts with --lifecycle=persistent and so has no watcher at all.

    The Control role (proto::ConnectionRole::Control, ClientHello::role) is for connections that ask the daemon about itself: no session is spawned for it (an unknown role byte decodes as Control, so a future role can never spawn one), it is not counted in the census and it does not subscribe to the host's stream. It carries DaemonStatusRequest (tag 25), answered by DaemonStatusReply (tag 26: process id, release, uptime, socket, executable, log file, sessions, clients, lifecycle) and StopDaemon (tag 27) with a StopReason (User or UpgradeRestart). ServerHello::releaseVersion is appended to the hello and tells a client which release it met, which is what drives the GUI's drift badge (vthost::client::assessDrift). Bodies are append-only: a daemon that predates a field leaves it at the decoder's default, and a PDU tag it does not know is answered with Unsupported. contour daemon status|stop|logs and the GUI's restart reach the daemon through client::DaemonControlPort (makeDaemonControl), whose connect failure is typed (ControlErrorCode::NotRunning for a missing or refused socket) rather than a string the caller parses.

    DaemonConfig::beforeShutdown is the seam for persistent workspaces: the funnel calls it with the ShutdownCause before any listener closes, after the daemon's own last snapshot (see Workspace snapshots).

    Sessions leave through exactly one funnel, SessionHost::handleSessionExit: a shell exiting (the pump thread's posted completion), the native ClosePane PDU, or control mode's kill-pane. The orphan reaps after a refused createTab deliberately do not fire sessionClosed, so a failed creation is never mistaken for the last session ending.

    Two details in LastSessionWatcher are load-bearing:

    • The trigger is edge-triggered, never a level check. The daemon binds its sockets with zero sessions and only gains one when a client asks — attaching to a daemon with no tabs spawns the first session. "No sessions, therefore quit" would end the daemon before anyone could attach.
    • The decision is deferred one pump, then re-checked. sessionClosed fires from inside SessionHost's observer fan-out, which the shutdown would mutate as connection flows unwind. More importantly, buffered input is dispatched without touching the reactor (core::async::Task tail-transfers; PduPump and net::AsyncBufferedReader return buffered frames and lines without awaiting), so a ClosePane followed by a CreateTab — or kill-pane then new-window — arriving in one read is fully dispatched before the loop regains control. The posted check therefore sees the batch's end state and the daemon survives.

    Shutdown is abrupt by design: requestStop cancels each connection's parked read, so the graceful epilogues (NativeSession's flushThenClose, control mode's %exit) are skipped. Peers see a clean FIN with no goodbye — which is exactly how a real tmux kill-server looks to them, and frames are enqueued whole so none is ever truncated. Closing a unix listener also unlinks its socket file, so the next ensureDaemon probe fails and spawns a fresh daemon rather than finding a dead path.

    One consequence worth knowing when shutting a daemon down by signal: a session whose shell is still running blocks teardown, because ~HostedSession joins a pump thread parked in a blocking PTY read. The last-session path is unaffected (its sessions are already gone by then).

    Workspace snapshots

    A daemon whose DaemonConfig::persistence names a file keeps its workspace there (SessionSnapshotStore), and offers Capability::WorkspaceRestore (8) while it does; that capability is what turns client::layoutSurvivesRestart to Restored, and with it the drift confirmation's text. runDaemon wires it in this order:

    1. the control socket is bound first, so a second daemon on the same label fails before it touches the file the serving one keeps writing;
    2. prepareRestore loads the file and moves it aside to <file>.restored, and the result becomes SessionHostConfig::restore, which the host realizes in its constructor instead of the startup layout (unless nothing of it came back);
    3. after the host, a DaemonPersistence closes the restore (endRestore), then owns the SnapshotWriter (its own thread, started after the signal watch so it inherits the blocked SIGINT/SIGTERM) and the WorkspacePersistence observer that decides when to write;
    4. the funnel's hook runs finalize(workspaceFor(cause)) and only then the caller's beforeShutdown. workspaceFor discards for StopRequested alone: a signal is how a reboot ends the daemon, a last session may have been killed by it, and --keep-snapshot is StopReason::UserKeepingWorkspace (2), which a daemon that predates it refuses rather than reads as a plain stop. The CLI therefore sends it only to a daemon whose hello offered WorkspaceRestore.

    On Windows the console-control handler returns only once that hook has run, for at most 4 s, for a close, a logoff or a system shutdown: Windows ends the process as soon as the handler returns. The watch is handed the hook's future (ShutdownSignals::watch's lastWrite) for that.

    The file, little-endian, every blob{…} decoded from a sub-reader of its own (bytes a reader does not know are skipped; absent trailing fields keep their defaults — phase 1's PDU body rule):

    File     := Magic Version:varint BodyLength:varint ChecksumLo:u32 ChecksumHi:u32 Body
Magic    := the 8 bytes "CTRSNAP\n"
Body     := TakenAt:svarint(unix seconds) WindowCount:varint Window{WindowCount}
Window   := blob{ Identity? ActiveTab:varint TabCount:varint Tab{TabCount} }
Tab      := blob{ Identity? Title:string? Color:u32(0xRRGGBB)? ActiveLeaf:varint Zoom:u8 Node }
Node     := blob{ Split:u8 ( Ratio:varint(millionths) Node Node | Leaf ) }
Leaf     := Identity? Cwd:string(UTF-8)? Profile:string? Foreground:string? CommandLine:string?
            History:blob(encodePdu(Delta))?
Identity := 16 raw bytes, Label:string?
X?       := u8 0 (absent) | u8 1 then X

    The checksum is FNV-1a 64 over Body. Cross-version readability is a requirement: the drift restart writes the file with the old daemon and reads it with the new one. A daemon reads every SnapshotFormatVersion an earlier release wrote, records grow only by appending inside their blob{…}, and the version steps only for a change an old reader would misread; an older daemon leaves a newer format in place instead of setting it aside. A history blob that does not decode drops only that pane's scrollback. The file is bounded (MaxSnapshotFileBytes, 64 MiB, and daemon.restore.scrollback_lines per pane), written to a private temporary sibling and renamed over the old one, and user-only (0600 in a 0700 directory; a protected DACL on Windows).

    A restore never loses the last good workspace: <file>.restored is deleted only by the first successful write after a restore that realized a pane. One that realized nothing keeps it for the next start, which tries it once more and then renames it <file>.failed.

    When to write is a pure table, decideSnapshotWrite (SnapshotSchedule.hpp), with the kill grace (5 s) and the layout debounce (1 s) of SchedulePolicy; now is T and lastKill the newest SessionEnd::Killed:

    Trigger Workspace Last kill Action
    Periodic clean any skip
    Periodic changed none, ≥ 5 s ago write now
    Periodic changed T−2 s defer to T+3 s
    LayoutChanged any none defer to T+1 s
    LayoutChanged any T−2 s defer to T+3 s
    SessionExited any none write now
    SessionClosedByRequest any none write now
    SessionExited, SessionClosedByRequest any T−1 s defer to T+4 s
    SessionKilled any any defer to T+5 s
    Shutdown any none, ≥ 5 s ago write now
    Shutdown any T−2 s skip: the file is kept as it was

    The kill grace is what makes a reboot restore anything. A system shutdown stops every shell before the daemon (systemd stops each shell's scope; a Windows logoff ends the ConPTY children), so the daemon sees its panes die moments before it is asked to end. A pane whose process was killed is therefore dropped from the file only after the grace, and a shutdown inside the grace keeps the file as it was. The kill is recorded in sessionEnded itself, not in a posted job: an ExitWhenEmpty daemon's LastSessionClosed shutdown is posted right after the last sessionClosed, and must already see it. A pane closed on request (ClosePane, kill-pane, through SessionHost::closeSession) or whose shell exited leaves the file at once.

    A periodic write that fails (a full or read-only state directory) leaves the previous file and no temporary behind, is logged once until a write succeeds again, and makes the next interval retry.

    Where a daemon runs from

    Where an upgrade would disturb the running binary — an AppImage, a macOS .app, a Windows install — a daemon runs from this version's copy under <state-dir>/bin/ (DaemonBinary.hpp, over DaemonImage.hpp's store); a packaged Linux install runs in place. A launcher (ensureDaemon, --background) spawns from the copy and keeps it leased until the daemon serves; a daemon started from the installed binary re-executes from the copy before it binds (relocationFor), keeping its process id, with the lease handed across the execv. contour daemon --in-place refuses the move.

    Which layouts stage is a table (stagingPlan(StagingInputs) → StagingLayout): an AppImage stages the AppImage file, macOS the whole .app (symbolic links such as a framework's Versions/Current are preserved, because a flattened bundle can fail code-signature validation), Windows the install tree (bin and share/contour), and a packaged Linux install does not stage at all — /usr/… and a Flatpak's /app/… are replaced atomically by the package manager, which a running daemon survives, and copying ~474 MB per release for nothing would be a cost without a benefit. The state directory (daemonStateDirectory, StatePath.hpp) decides where copies go; when it is the temporary fallback the store stages nothing, since that directory is shared with other local users and a launcher must not execute a binary one of them could have planted.

    Publishing is the rename of a complete directory: two launchers staging the same release at once each copy into their own partial directory and rename it into place; the loser finds the target complete and uses it. An incomplete target (no .complete marker) is removed under the held lease before the rename is retried once.

    A lease is a file beside the image (<release>-<fingerprint>.lease, a sibling so that removing the image never removes the lock). Whoever runs from an image, or is about to, holds its lease; on POSIX that is an advisory flock, re-checked against the path's device and inode after it is taken so a concurrent prune cannot slip between the open and the lock. prune takes a claim() — an exclusive, non-blocking lock — and removes the image, its partial copies and the lease file only while holding it; a held lease stops the prune. A launcher takes the lease when it stages the image and holds it until the daemon it spawned serves (or the spawn fails), so a second, newer launcher pruning in that window cannot remove it; the daemon then holds its own for its lifetime. Each of them prunes once its own lease is held: the launcher after staging, the daemon in leaseRunningImage. The daemon's prune is the only one a daemon started by a service manager gets, since no launcher runs for it. Leases open O_CLOEXEC, so shells and xdg-open do not inherit them; the flag is cleared just before a daemon's re-execv from the copy and set again by the re-executed daemon.

    Manual check for an AppImage, which no CI job runs: start Contour.AppImage daemon and confirm that the pid started is still the daemon, that APPIMAGE in its /proc/<pid>/environ names $XDG_STATE_HOME/contour/bin/<release>-<hash>/Contour.AppImage, that the .lease beside that directory is listed by ls -l /proc/<pid>/fd, and that deleting the original AppImage file leaves the daemon serving.

    Binary imsg IPC (the real tmux binary as a client)

    The daemon's third endpoint, <control-socket>-tmux, speaks tmux's binary client protocol — the rewritten libutil imsg tmux ≥ 3.6 uses: 16-byte host-order {type,len,peerid,pid} header, len including the header with its top bit marking one SCM_RIGHTS descriptor, masked length in [16, 16384], peerid's low byte carrying PROTOCOL_VERSION (8; a mismatch answers MSG_VERSION and drops). The insight that makes this cheap: control mode rides ON TOP of imsg. After the MSG_IDENTIFY_* handshake (a data-driven table validates payload shapes exactly as the real server does) passes the client's STDIN/STDOUT via SCM_RIGHTS and an attach-shaped MSG_COMMAND arrives, the ORACLE-VERIFIED control-mode engine simply runs over the passed descriptors (net::adoptFd + net::combineHalves); the imsg socket carries only lifecycle. So tmux -S <socket>-tmux -C attach-session works with the stock tmux binary — proven by an oracle test forking the real client, and live against the shipped daemon.

    Deliberate deviations from the real server, all verified against the reference tree (3.7b-617-g5ed5e360):

    • acceptance requires CLIENT_CONTROL and refuses -CC (CLIENT_CONTROLCONTROL) — we never render a full terminal client; rejections answer MSG_EXIT with a message, as tmux's own idiom does;
    • the startup command is a table (attach-session/attach/ new-session/new/empty ⇒ attach); arbitrary startup commands are not executed;
    • the %exit line is SUPPRESSED on this path — the tmux client binary prints its own after its imsg loop ends — and the preamble guard pair is stamped flag 0 (the MSG_COMMAND-originated command is not client-originated in cmd-queue terms), while stdin-line commands keep 1;
    • a detach drains the control stdout fully, THEN sends MSG_EXIT (mirroring control_all_done gating); MSG_EXITING is answered with MSG_EXITED;
    • the socket's execute-bit "has attached clients" signal is not maintained (verified informational: no tmux client reads it before connecting).

    contour daemon --tmux-compat-socket LABEL additionally binds tmux's own discovery path /tmp/tmux-<uid>/LABEL, so a plain tmux -L LABEL -C attach-session finds the daemon. Opt-in only: with the daemon down, a new-session on that path would silently fork a REAL tmux server onto it.

    Windows

    The Win32 net backend serves AF_UNIX via afunix.h (Windows 10 1803+); the socket's parent directory is created but NOT permission-hardened — NTFS ACLs govern access, not POSIX mode bits. runDaemon serves the control and native endpoints (no imsg: SCM_RIGHTS does not exist on Windows), with SetConsoleCtrlHandler marshaling shutdown onto the loop. Sessions are ConPTY-backed, exactly as the GUI's local ones are.

    Starting without a terminal

    contour daemon --background relaunches its own argv with --background=false appended, through spawnDetachedDaemon, then blocks on spawnAndAwaitDaemon until the native socket accepts — so returning means "it is serving", not "the process started". Replaying its own tokens rather than rebuilding them from parsed flags (crispy::app::commandLine) is what keeps a new daemon option from being silently dropped by a second, forgotten spelling of the flag list.

    The flag is overridden rather than filtered out of that argv, because crispy::cli spells it four ways — --background, -background, the bare background (its natural style), each optionally with a value in the =VALUE or separate-token form — and options are last-one-wins. A token filter that misses a spelling makes the child spawn another detached child, for ever.

    On POSIX the child calls setsid() and reopens its standard descriptors on /dev/null before execv, which is what DETACHED_PROCESS buys the Windows branch: a daemon left in the invoking shell's session and foreground process group takes the terminal's Ctrl-C (killing every hosted session) and dies outright on the SIGHUP of a closing terminal, which runDaemon does not block. Its diagnostics go to --log-file, which this path always supplies.

    contour daemon-service install|uninstall|start|stop|restart|status registers that daemon with the OS. Two mechanisms hide behind the verbs, because on Windows no single one does both halves of what is wanted (vthost/ServiceControl.hpp):

    --start Backend Trigger Elevation Password
    logon (default) Task Scheduler 2.0 (COM) the installing user's logon no no
    boot / manual SCM service boot / on demand yes yes

    The public service-trigger set has no logon trigger — SERVICE_AUTO_START means boot, in session 0 — and CreateServiceW under a named account needs that account's password, where a task registers with TASK_LOGON_INTERACTIVE_TOKEN and needs none. So the start mode selects the backend, and logon is the default: a multiplexer is per-user and per-session, and a shell spawned from session 0 runs in the service's window station where any GUI program it launches is invisible. The SCM backend is not implemented yet (it needs the credential prompt plus a StartServiceCtrlDispatcherW mode in the daemon, which would be a fourth shutdown trigger alongside the three above); boot/manual report exactly that rather than quietly registering under LocalSystem, whose different %TEMP%/%USERNAME% would bind a socket no client could find.

    The logon trigger is bound to the installing user's SAM name, not left blank — a blank one fires on any user's logon.

    Each backend declares a DaemonLaunchStyle. A SelfDetaching backend (the Task Scheduler: it starts a launcher, and the daemon backgrounds itself, so the OS does not track the daemon's process) cannot stop the daemon by ending a unit. For such a backend daemon-service stop, restart and uninstall stop the daemon through StopDaemon on a Control connection, chosen by the table stopVia(DaemonLaunchStyle); a tracked backend (systemd, launchd) is stopped through the service manager, which also keeps it from restarting a daemon that was stopped on purpose. The decision is portable code and tested on Linux with fakes; the Task Scheduler calls themselves are compiled only on Windows. The Windows image store (DaemonImageLeases_win32.cpp) is likewise compiled only there.

    The client side is the GUI (contour client) on Windows as everywhere else. There was briefly a console client here — runAttach, raw VT console mode plus a dedicated blocking stdin-reader thread, since console handles cannot park on the socket reactor — and it was dropped along with the TUI thin client (d4ce9c96); a future TUI mode plugs back in at the same seam. The console handling is the part worth remembering if it ever returns.

    Windows code is exercised by the Windows CI job (compile under -Werror plus the runtime-gated unix-echo net test); it cannot run on the Linux development machines.

    Diagnostics

    The daemon logs through crispy::logstore. Categories are dotted and module-first, so vthost.* maps 1:1 onto src/vthost/; contour list-debug-tags prints them all.

    Category Default What it records
    vthost.daemon on Endpoints bound, listeners started, signals, shutdown. Banner-grade only — with no --log and no $LOG these lines are the foreground user's only feedback.
    vthost.conn off Per-connection accept, handshake and disconnect.
    vthost.session off Hosted session spawn, resize, model refusal, exit.
    vthost.tmux off Control-mode and imsg attach/rejection.
    vthost.client off The attach side of the native protocol.
    vthost.trace.proto off One line per PDU, both directions.
    vthost.trace.tmux off Every control-mode line, both directions.

    Genuine failures — malformed frames, rejected handshakes, refused sends — go to the always-enabled error category, deliberately with no category of their own: they must be visible without anyone having thought to enable a filter first. core::log::configure therefore keeps error on no matter what the filter selects.

    net has no categories at all. It returns every failure as a std::expected<…, NetError> whose context carries the detail (including the OpenSSL text on a TLS handshake), and the connection that owns the transport prints it with its identity — so logging inside net would only duplicate that line, minus the part that makes it useful.

    Selecting and directing output

    contour daemon --log 'vthost.conn,vthost.session'   # a specific pair
contour daemon --log 'vthost.*'                     # everything, TRACE INCLUDED (see below)
contour daemon --log 'vthost.trace.*' --log-file /var/log/contour-daemon.log
LOG='vthost.*' contour daemon                       # the environment variable still works

    Three behaviours worth knowing:

    • * is a plain prefix match, so vthost.* sweeps in vthost.trace.* too — exactly as vt.* already sweeps in vt.trace.sequence. Name vthost.trace.* to select the trace tier alone, or list categories explicitly to exclude it.
    • A filter is a selection, not a union: core::log::configure disables every category the filter does not name. error is deliberately exempt — asking for extra detail must never take failure reporting away.
    • --log-file appends and never writes SGR escapes, so a daemon restarted against the same file does not erase why the previous run died. --log-file - means standard error explicitly.

    contour client accepts both options and passes them to a daemon it auto-spawns. That matters more than it looks: the auto-spawned daemon is the common case, and without this it is the one instance nobody can configure, whose standard error lands in the client's terminal. The whole spawn command line — the socket, these two options and --lifecycle=exit-when-idle — is built once in daemonSpawnArgs, so the POSIX execv argv and the Windows CreateProcess command line cannot drift apart.

    Correlating a connection

    Every line about one connection carries its identity — <endpoint>#<n>, plus @<peer> where the transport knows one — so a whole connection reads as one story:

    [vthost.conn]        native#3: accepted
[vthost.trace.proto] native#3 recv #1 ClientHello versions=4-4 caps=1 token=yes settings=yes (60 bytes)
[vthost.conn]        native#3: handshake complete (protocol v4)
[vthost.trace.proto] native#3 send #0 Delta session=1 gen=3 seq=98 lines=7 (412 bytes)
[error]              native#3: malformed frame (MalformedVarint); dropping the connection

    The endpoint name is constructor-injected into each ConnectionAcceptor (control, native, imsg, tmux-compat, native-tcp) and travels to the connection flow as a ConnectionId.

    What a trace deliberately does not show

    proto::summarize reports sizes, never payloads: Input gives a byte count, Delta a line count, SessionState the lengths of the title and cwd. A ClientHello's preshared token is reported only as present or absent. A trace of a busy session must not become a transcript of the user's keystrokes or screen contents, and a token mismatch — which the wire answer deliberately makes indistinguishable from a version mismatch — must not be undone on disk.

    Adding a PDU to the catalog means adding one row to TraceTable in proto/PduTrace.cpp; a static_assert against std::variant_size_v<DecodedPdu> makes forgetting it a build break.

    Threading

    Every emission point runs on the event-loop thread. Session pump threads marshal through EventLoop::post before anything logs, and both shutdown hooks (the POSIX sigwait thread and the Win32 console-control handler) log from inside their posted continuation rather than the handler body. logstore has no synchronization of its own, so the daemon's sink serialises write-and-flush under a mutex; that covers the residual cross-thread cases.
