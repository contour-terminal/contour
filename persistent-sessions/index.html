    Persistent sessions (daemon mode)

    Experimental

    Daemon mode is new in 0.7.0 and still settling. It is built into every Contour and covered by the test suite, but its command-line flags and its wire protocol may change between releases.

    Contour already gives you tabs and split panes inside one window. Daemon mode is different: it moves your sessions into a background process, so they survive the window that shows them. Close the window, reattach later, or attach from another machine — the shells keep running either way.

    That buys you three things:

    • A long build, a database migration or a training run keeps going after you close the window — deliberately or by accident.
    • Work done over SSH survives the link dropping. Reconnect, reattach, carry on.
    • The same sessions are reachable from a second machine, over an encrypted connection.

    If you have used tmux or screen, this is the same idea, with two differences: the sessions are rendered by a real Contour window (images, hyperlinks, sized text and all), and Contour can speak tmux's own protocol in both directions — so it interoperates with tmux rather than replacing it.

    Quick start

    contour client

    That is the whole thing. contour client looks for a daemon, starts one if none is running, and opens a window showing its sessions. Close the window and the shells stay alive; run contour client again to pick them back up — with their scrollback, so you can scroll back through what the session did while nothing was watching.

    To manage the daemon yourself, start it first:

    contour daemon &      # runs in the FOREGROUND; background it or use a service manager
contour client        # attaches to the daemon you started

    The distinction matters, because the two daemons have different lifetimes:

    How it started When it exits
    Auto-started by contour client 10 seconds after it has no sessions and no clients — it belongs to the clients that needed it, so nothing is left behind
    Started by you (contour daemon) Never on its own. It keeps serving with zero sessions, ready for the next client
    Started by the OS (contour daemon-service) Never on its own, see Starting the daemon at login

    Closing the last window therefore keeps your sessions: the auto-started daemon stays up as long as any session lives, and for 10 seconds after the last one is gone and the last client has disconnected. A client that attaches within those 10 seconds keeps the daemon alive.

    The policy is the daemon's --lifecycle option, and it rides on the daemon, not on the client that started it:

    --lifecycle The daemon ends
    persistent (default for contour daemon) never on its own
    exit-with-last-session once its last hosted session is gone (tmux spells this exit-empty)
    exit-when-idle (what contour client starts on demand) 10 seconds after it has no session and no client

    --exit-with-last-session is kept as an alias for --lifecycle=exit-with-last-session. Stating both is an error only when they differ. A status probe (contour daemon status) is not a client and never keeps an idle daemon alive.

    contour daemon does not detach by itself

    It runs in the foreground and logs to standard error, which is what you want under a service manager or in a container. Background it with &, or let contour client start it for you.

    Detaching versus ending a session

    Because sessions outlive the window, "close" needs two answers — and Contour gives you both. Which one you get depends on what you close:

    What you close What happens to the shell
    The window (its close button, or quitting Contour) Detach. It keeps running; the next contour client shows it again
    A pane — Close Pane in the right-click menu, or the ClosePane action Ends. That session is closed on the daemon and does not come back
    A tab — its ✕, or the CloseTab action Ends, together with every pane in it
    Typing exit in the shell Ends, as always — the shell decided

    This is the same split tmux draws between detaching a client and kill-pane, and it works the same for a local session as for one hosted by a daemon: a pane you end is ended everywhere, including for any other client attached to that daemon.

    Neither ClosePane nor CloseTab ships with a default key binding — bind them yourself if you want one:

    input_mapping:
    - { mods: [Ctrl, Shift], key: 'W', action: ClosePane }

    Ending a whole daemon's worth of sessions

    Closing panes one at a time is the fine-grained way. To end everything at once, stop the daemon — see Stopping a daemon.

    Running several daemons side by side

    Daemons are told apart by a label, exactly as tmux's -L does:

    contour daemon --label work
contour client --label work

    The label names a socket under your per-user runtime directory. Resolution order:

    1. --socket PATH — used verbatim.
    2. $CONTOUR_MUX — used verbatim (analogous to tmux's $TMUX).
    3. $XDG_RUNTIME_DIR/contour/<label>.
    4. <temp>/contour-<uid>/<label> when there is no runtime directory (tmux's /tmp/tmux-<uid>/<label> shape).

    The daemon binds three endpoints, all derived from that one path: the control socket itself, <socket>-native for Contour's own clients, and <socket>-tmux for the tmux binary.

    The socket directory is created 0700 and checked on every bind: it must be a real directory, owned by you, and must not be world-accessible. Group access is permitted, matching tmux.

    Keep socket paths short

    A Unix socket path is limited to roughly 100 bytes by the operating system, not by Contour. A deeply nested --socket path will fail to bind.

    contour daemon options

    Option What it does
    --socket PATH Path of the control socket file. Defaults to the configuration's daemon.socket, else $XDG_RUNTIME_DIR/contour/LABEL, respecting $CONTOUR_MUX.
    --label NAME Socket label distinguishing daemon instances. Default default.
    --config FILE Configuration file whose profile supplies the hosted sessions' terminal settings — including history.limit, which is how much scrollback a session keeps for clients that attach later.
    --profile NAME Which profile of that configuration to take them from. Defaults to the configuration's default profile.
    --lifecycle POLICY When the daemon ends on its own: persistent (the default), exit-with-last-session or exit-when-idle. See Quick start.
    --exit-with-last-session Alias for --lifecycle=exit-with-last-session.
    --size-policy POLICY Which attached client's size the shared grid takes when clients of different sizes are attached: latest, smallest or largest. Mirrors tmux's window-size. Defaults to the configuration's daemon.size_policy (latest unless set).
    --background Relaunches the command detached and returns once the daemon accepts connections. Without --log-file the daemon logs beside its socket (SOCKET.log), since a detached process has no console.
    --stdio Relays the native protocol between standard input/output and this user's daemon, starting it if needed: what contour client --host runs over ssh. Honours --label, --socket, --config, --profile, --log, --log-file and --size-policy (forwarded to a daemon it starts); cannot be combined with --listen-tcp, --background or --tmux-compat-socket.
    --in-place Runs from the installed binary instead of a per-version copy. See After upgrading Contour.
    --tmux-compat-socket LABEL Additionally binds tmux's own discovery path /tmp/tmux-<uid>/<LABEL>, so a plain tmux -L LABEL -C attach-session finds this daemon.
    --listen-tcp HOST:PORT Also serve the native protocol over TCP. Opt-in; always TLS-encrypted and token-authenticated. See Remote access.
    --token TOKEN Preshared token every TCP client must present. Required with --listen-tcp. Visible to other local users through the process list — prefer --token-file.
    --token-file FILE Reads the token from FILE instead, so the secret is protected by that file's permissions. Trailing newlines are ignored.
    --access-file FILE Further TCP tokens with narrower grants, one per line. Needs --listen-tcp. See Narrower tokens.
    --tls-cert FILE, --tls-key FILE PEM certificate and matching private key for the TCP listener. Omit both to have the daemon generate an ephemeral self-signed certificate.
    --log TAGS Enable logging for a comma-separated list of tags, or all. See Diagnostics.
    --log-file FILE Append log output to FILE instead of standard error; - means standard error explicitly.

    Hosting from a plain contour

    The thin client is the default: a plain contour shows sessions that a daemon hosts, starting that daemon when none runs. contour client always attaches; a plain contour decides by daemon.mode in the configuration, or by --daemon-mode on its command line:

    Mode Where the sessions run
    auto (the default) In the daemon, started if none runs; when none can be had, in the window's process, with a bar saying why — those shells end when the window closes
    in_process In the window's own process, as before daemon mode existed
    required In the daemon, or not at all: the launch ends with the reason before any window opens 
    daemon:
  mode: auto          # auto, in_process or required
  socket: ""          # the daemon's socket path; empty selects the default
  size_policy: latest # whose size wins when clients disagree: latest, smallest or largest
  history_limit: 1000 # scrollback lines per session, -1 for unlimited; unset follows the profile

    contour --daemon-mode in_process   # this launch only: keep the sessions in this window
contour --daemon-mode required     # this launch only: fail rather than fall back

    What a launch opens

    An attaching launch opens one new window beside whatever the daemon already shows. When no other window is attached to the daemon, it instead brings every window the daemon holds back, so reopening Contour after closing its last window finds your sessions where you left them.

    A launch that names a program (-e, or a command after the options) runs it in the window's own process under auto; under required it ends before any window, since a daemon session runs the host's profile.

    When the connection is lost

    A window attached to a daemon keeps its panes when the connection drops. They show "Reconnecting…" while the window reconnects with backoff (250 ms doubling to 5 s) and picks its windows up again. A connection gone half-open — a laptop that changed networks — is noticed by a heartbeat within about 15 s instead of whenever TCP gives up. Input typed while disconnected is dropped rather than replayed into whatever shell answers next. A launch that falls back to in_process has no connection to lose.

    contour client options

    Option What it does
    --socket PATH, --label NAME Which daemon to attach to; same resolution as above, daemon.socket of the client's configuration included.
    --window ID Show only the daemon window ID instead of opening a new one; fails, naming it, when the daemon has no such window.
    --size-policy POLICY The policy a daemon this client auto-starts runs with; defaults to daemon.size_policy.
    --tmux Attach to a real tmux server instead of a Contour daemon. See tmux interoperability.
    --tmux-socket PATH The tmux server socket (tmux's -S) for --tmux.
    --profile NAME Config profile the window renders remote sessions with.
    --config FILE Configuration file to load.
    --host NAME\|URL Attach to a remote host: a name saved under hosts:, or an ad-hoc ssh://[USER@]HOST[:PORT] (a tls:// host needs its token, so it must be saved). The remote daemon is started there when none runs; every one of its windows is shown, and the window title and the tab strip name the host. A host's profile: is used unless --profile names one. Cannot be combined with --socket, --connect-tcp, --token, --token-file, --tls-ca or --tmux. See Remote hosts.
    --connect-tcp HOST:PORT Connect to a remote daemon over TLS instead of a local socket.
    --token TOKEN, --token-file FILE The preshared token to present, inline or read from a file.
    --tls-ca FILE PEM trust anchor pinning the daemon's certificate. Omitted means encrypt-but-do-not-verify.
    --log TAGS, --log-file FILE As above — and passed on to a daemon this client auto-starts, which is otherwise the one instance nobody can configure.

    tmux interoperability

    Contour speaks tmux's control-mode protocol in both directions, pinned to tmux 3.7b semantics.

    Attach tmux tooling to a Contour daemon

    <socket>-tmux speaks the binary protocol the stock tmux client uses, so the real tmux binary can attach to a Contour daemon:

    tmux -S "$XDG_RUNTIME_DIR/contour/default-tmux" -C attach-session

    To let tmux find the daemon by label alone, have the daemon bind tmux's own discovery path too:

    contour daemon --tmux-compat-socket mine
tmux -L mine -C attach-session

    --tmux-compat-socket is opt-in for a reason

    That path is where tmux looks for its server. With the Contour daemon down, a new-session against it would silently start a real tmux server there instead.

    Control mode (-C) is supported; -CC is not — Contour never renders a full terminal client for tmux. Arbitrary startup commands are refused; the endpoint accepts attach- and new-session-shaped startup only.

    Show a real tmux server in a Contour window

    The other direction: point Contour at a tmux server and mirror it.

    contour client --tmux                       # the default tmux server
contour client --tmux --tmux-socket /tmp/x  # a specific one

    tmux windows become Contour tabs, tmux panes become splits, and input travels back as send-keys. Content mirrors live.

    tmux replay carries text, not images

    Contour replays each pane's full history through capture-pane, so scrollback survives a reattach on this path too. Images do not, and that is a tmux limitation rather than Contour's: capture-pane serialises text and colour, never image data. Images drawn while you are attached display normally; images drawn before you attached cannot be recovered. Contour's own native protocol has no such gap — it transfers images by id.

    Remote access over TCP

    By default a daemon is reachable only through its Unix socket, where the filesystem permissions are the access control. --listen-tcp additionally exposes the native protocol over the network:

    # On the host running the sessions:
umask 077 && openssl rand -base64 32 > ~/.contour-token
contour daemon --listen-tcp 127.0.0.1:9090 --token-file ~/.contour-token

# On the machine you are sitting at:
contour client --connect-tcp server.example.com:9090 --token-file ~/.contour-token

    Properties worth knowing before you open a port:

    • TLS is not optional. The TCP endpoint is always encrypted; there is no plaintext mode.
    • A token is required. TCP has no filesystem gate to fall back on, so --listen-tcp without --token/--token-file refuses to start rather than serving anonymously.
    • Prefer --token-file. A token passed as --token is readable by every other user on the machine through the process list; a file carries permissions.
    • Without --tls-cert/--tls-key the daemon generates an ephemeral self-signed certificate, and without --tls-ca the client encrypts but does not verify who it is talking to. That is a trust-on-first-use posture: it stops passive eavesdropping, not an active machine-in-the-middle. For anything beyond a trusted network, pass a real certificate on the daemon and pin it with --tls-ca on the client — the certificate must then also be issued for the host you connect to, not merely signed by that CA.
    • Bind deliberately. 127.0.0.1 reaches only the local machine; 0.0.0.0 reaches everyone who can route to you. Prefer forwarding the loopback port over SSH to exposing it directly.
    • Control requests need a verified daemon. A client of the control API refuses to send a single request over TLS it has not verified: without --tls-ca it stops before connecting. With the control API a token types into and reads every pane, so it must not be handed to whoever answers.

    Narrower tokens for scripts

    --token grants everything. A script that only needs to read a pane can be given a token of its own that grants less, through --access-file FILE, one entry per line:

    # grants   token (to the end of the line)
read,screen ci-reader s3cret
all admin-token

    A line is a grant list — all, or a comma list of read (look at the workspace), screen (read what is on screen and in command blocks), input (type into a pane) and write (change the workspace, stop the daemon) — one space, then the token, which may contain spaces. Carriage returns and trailing whitespace are dropped, as for --token-file; blank lines and lines starting with # are ignored. An unknown grant, an empty token or a token that appears twice stops the daemon from starting, naming the line. The file adds tokens beside --token/--token-file, never instead of them: a hello may present either, and the --token keeps granting everything, so moving everyone to the access file means removing --token as well. A line that repeats the --token stops the daemon from starting too, since its narrower grants would silently read as everything.

    Running a program is typing it: tab.create and pane.split with a command need input as well as write, so a token granted read,screen,write can open shells and rearrange the workspace but cannot run a program of its choosing in it. Events follow the same grants: block.finished carries the command line and needs screen, so a subscription of a read token is handed every other kind but that one, and a subscribe naming only kinds the token may not see is answered forbidden.

    A call outside a token's grants is answered forbidden and the connection stays open. Viewing the sessions needs every grant, so a contour client with a narrower token is refused exactly as with a wrong one.

    To attach over ssh instead, with no port to open, to save hosts by name, or to reach a home PC from the office over Tailscale, see Remote hosts.

    Starting the daemon at login

    Instead of letting contour client start a daemon when it is needed, you can have the operating system start one for you when you log in:

    contour daemon-service install      # register it (and start it with your next login)
contour daemon-service status       # registered? running? what does it run?
contour daemon-service start        # start it now
contour daemon-service stop         # stop it, leaving it registered
contour daemon-service restart
contour daemon-service uninstall    # stop it and remove the registration

    Each verb takes --label NAME (default default). install additionally takes --socket, --config, --profile, --size-policy, --log and --log-file, which are recorded in the registration. A socket path is made absolute at install time, because the registration outlives the shell that wrote it. Unless you give --log-file the daemon logs to SOCKET.log.

    OS What is registered Runs as
    Linux the systemd user unit contour-daemon.service (contour-daemon-LABEL.service for other labels), written to ~/.config/systemd/user and enabled you, no elevation
    macOS the LaunchAgent org.contourterminal.contour-daemon in ~/Library/LaunchAgents you, no elevation
    Windows a Scheduled Task triggered by your logon you, no elevation

    Packages for Linux also ship a contour-daemon.service unit file. It is not enabled by the package; contour daemon-service install writes your own copy, which takes precedence.

    A service-managed daemon runs with --lifecycle=persistent: it never exits on its own, not even with zero sessions and zero clients. contour client finds the registration and starts it before it falls back to spawning a daemon on demand. A registration made by an older release under another name is found as well.

    --start boot and --start manual (a Windows service) are not implemented yet.

    Stopping a daemon

    Ask it to stop, from anywhere:

    contour daemon stop           # asks first when the daemon hosts sessions
contour daemon stop --yes     # does not ask
contour daemon status         # is one running? version, uptime, socket, sessions, clients
contour daemon logs           # the last 100 lines of its log
contour daemon logs --follow --lines 20

    All of them accept --label and --socket, written before or after the verb. Giving the same option before and after the verb with different values is a usage error, so that stop never silently targets another daemon than the one you named. When no daemon answers, status and stop exit with status 4. stop asks for confirmation only when sessions exist; without a terminal it refuses unless you pass --yes. logs shows the file the daemon reports as its log; if none is running it falls back to the default SOCKET.log beside the socket, and says so.

    A daemon started from a terminal also stops on SIGINT or SIGTERM — Ctrl+C if it is in the foreground, or kill <pid>. On Windows, a console-control event does the same. A daemon that predates contour daemon stop answers that it does not support it; stop it where it runs, or end its process.

    For a service-managed daemon, prefer contour daemon-service stop, which lets the service manager know it was stopped on purpose rather than restarting it.

    Shells do not survive the daemon

    Persistence is against the client, not against the daemon process. Stopping the daemon ends every shell it hosts. Shutdown is abrupt by design — attached clients see the connection close with no goodbye, exactly as a real tmux kill-server looks to them. What comes back after a reboot, a crash or an upgrade is the workspace — see Surviving reboots.

    Surviving reboots

    A daemon keeps a snapshot of its workspace, so that after a reboot, a crash or an upgrade the next daemon brings it back. The shells themselves cannot survive their daemon; what returns is:

    • every window, tab and split, with its ratios, the active tab and pane, and a zoomed pane;
    • tab titles and the tab colours you set;
    • each pane's working directory and profile;
    • the newest lines of each pane's scrollback, under a dim marker row such as ── restored · snapshot of 2026-10-24 09:15 ──, followed by a fresh shell.

    The snapshot is written every interval seconds while the workspace changes, at once when you close a pane or a tab, and once more as the daemon ends. It is restored when a daemon starts and finds one: after a reboot, a crash, a SIGTERM, an idle exit, or the restart the drift chip offers after an upgrade (see After upgrading Contour). It is not restored after a plain contour daemon stop, which empties it, and panes and tabs you closed are not brought back.

    contour daemon stop                   # ends the shells and discards the workspace
contour daemon stop --keep-snapshot   # ends the shells; the next daemon restores the workspace

    With no daemon running, contour daemon stop still offers to empty the saved workspace, so a daemon started later does not bring back what you meant to end. Since a crash may have left that workspace as all you have, it asks first, unless --yes is given, and without a terminal to ask on it clears nothing and tells you to pass --yes. It exits with status 4 as before, whether it cleared the workspace or you kept it; with nothing saved it says so and creates no file. A daemon from a release before this feature keeps no workspace: --keep-snapshot then says so and stops it plainly.

    A program is never started again by itself. Only one you list in rerun_programs is run once more when its pane was running it, and only when its command line holds nothing a shell would expand. When the saved directory no longer exists, the pane opens in the shell's default directory and the daemon logs it.

    daemon:
  restore:
    scrollback: true          # bring the scrollback back
    scrollback_lines: 1000    # the most lines kept per pane, 0 to 100000
    rerun_programs: []        # e.g. [vim, htop]; nothing is re-run unless listed
    interval: 30              # seconds between writes of a changed workspace, at least 5

    scrollback_lines bounds the snapshot only; how much scrollback a session holds while it runs stays daemon.history_limit.

    The snapshot is <state-dir>/sessions/<label>.snapshot (the state directory is listed under Platform notes); a daemon started with --label work keeps work.snapshot. A daemon given a socket of its own, by --socket or $CONTOUR_MUX, keeps <label>@<hash>.snapshot instead, the hash naming its socket, so it never restores or overwrites the workspace of the daemon its label runs; contour daemon stop --socket finds the same file. The file is your user's alone: mode 0600 in a 0700 directory on Linux, macOS and BSD, and a protected ACL granting only your account on Windows. It is replaced atomically and durably: each write is flushed to the disk before it replaces the previous snapshot, and the replacement is flushed in turn, so a daemon crash, a power loss or a kernel crash in the middle of a write leaves either the previous snapshot or the new one, whole.

    The snapshot may hold secrets

    Restored scrollback is whatever was on screen: a password echoed by mistake, a token printed by a tool. It is written to disk in the clear. Set scrollback: false to keep only the layout and the directories, or scrollback_lines: 0 for the same.

    A snapshot that cannot be read is renamed <label>.snapshot.corrupt and the daemon starts with its startup layout, logging why; one written by a newer release is left in place. A restore that brought nothing back is tried once more at the next start, then set aside as <label>.snapshot.failed.

    Diagnostics

    The daemon logs through Contour's category system; contour list-debug-tags prints every tag. The vthost.* categories are the daemon's:

    Category Default What it records
    vthost.daemon on Endpoints bound, listeners started, signals, shutdown
    vthost.conn off Per-connection accept, handshake, disconnect
    vthost.session off Session spawn, resize, exit
    vthost.tmux off Control-mode and tmux-binary attach or rejection
    vthost.client off The client side of the native protocol
    vthost.trace.proto off One line per protocol message, both directions
    vthost.trace.tmux off Every control-mode line, both directions 
    contour daemon --log 'vthost.conn,vthost.session'
contour daemon --log 'vthost.*' --log-file /var/log/contour-daemon.log

    Three behaviours to know:

    • * is a plain prefix match, so vthost.* sweeps in the verbose vthost.trace.* tier as well. Name vthost.trace.* to select the trace tier alone.
    • A filter is a selection: it disables the categories it does not name. Real failures are exempt — asking for extra detail never takes error reporting away.
    • --log-file appends and never writes colour escapes, so restarting a daemon against the same file does not erase why the previous run died.

    Traces report sizes, never payloads: a keystroke message shows a byte count, a screen update a line count, and a token only as present or absent. A trace of a busy session must not become a transcript of what you typed.

    Platform notes

    Contour keeps what outlives a daemon in a per-user state directory, separate from the runtime directory the sockets live in:

    OS State directory
    Linux, macOS, BSD $XDG_STATE_HOME/contour when set and absolute, otherwise ~/.local/state/contour
    Windows %LOCALAPPDATA%\contour

    Without a usable home directory the fallback is <temp>/contour-state-<user>. That directory is shared ground, so a daemon never runs from a copy staged there: it runs in place instead.

    Daemon mode works on Linux, macOS, BSD and Windows 10 1803 or newer, over Unix domain sockets everywhere. On Windows, sessions are backed by ConPTY, the socket directory is governed by NTFS ACLs rather than POSIX permission bits, and the tmux-binary (<socket>-tmux) endpoint is absent — it needs file-descriptor passing, which Windows sockets do not have.

    After upgrading Contour

    An upgrade never touches the running daemon. The daemon keeps serving, and the client you start next may be newer than the daemon it attaches to.

    Where an upgrade would disturb a running binary, the daemon does not run from the installed binary at all. On Windows (the installer replaces contour.exe and the Restart Manager kills whoever holds it), on macOS (swapping the .app breaks the lazy loading of its frameworks) and for an AppImage (its mount vanishes when the AppImage process exits), a daemon runs from a copy of its own release under <state-dir>/bin/<version>-<id>/. It is made the first time that release starts a daemon, and removed again once no daemon runs from it.

    What the copy costs

    A release contour binary is about 474 MB. On Windows the copy is the whole install folder, on macOS the whole .app, and one such copy exists per release that has a daemon running or about to start, until it is unused. Old copies are pruned automatically, never while a daemon runs from them.

    A packaged Linux install (/usr/..., Flatpak /app/...) runs in place, which a package upgrade cannot disturb. contour daemon --in-place opts out of the copy; a package upgrade may then replace the binary under the running daemon. A hand-started foreground contour daemon on Windows also runs from the installed binary.

    The two negotiate a protocol version when they connect: each states the range of versions it speaks, and they agree on the newest one both know. Every release speaks the protocols of at least the previous two releases, so a client from a newer release attaches to an older daemon — and an older client to a newer daemon — as long as the two are within that window. Features the older side does not know are simply not used on that connection.

    When the daemon's release differs from the client's, the window shows a quiet chip at the bottom right, for instance daemon 0.8.1 is older than this client. Clicking it offers Restart daemon on the new version. The confirmation says what that costs: it ends every shell the daemon hosts, and a fresh one opens on the new daemon. A daemon that keeps its workspace brings your windows, tabs, directories and scrollback back, and the confirmation says so (see Surviving reboots). After the restart a new Contour window attaches to the new daemon, and this one closes. The chip is shown only for the local daemon: a remote one (--connect-tcp) is not yours to restart.

    The restart stops the daemon for an upgrade, then starts one the same way a client would: through the registered service when there is one, on demand otherwise.

    Outside the window, or against a daemon from Contour 0.7.0 or another release before version negotiation, the client is refused, and it tells you both sides' versions:

    the daemon speaks protocol 3, from a release before version negotiation; this client speaks 4-4

    A wrong token is reported as such instead (wrong token or insufficient rights): the refusal names the daemon's versions either way, so a probe learns nothing more from it. To move past a version refusal, stop the daemon and let it start again:

    contour daemon stop
contour client                        # starts a matching daemon

    Remember that this ends the sessions it was hosting. An auto-started daemon rarely has the problem, since it exits 10 seconds after its last session and client are gone.

    Current limitations

    • contour client opens a window. There is no terminal-only client at present; if you need one, attach with tmux -C through the compatibility endpoint described above.
    • You get the scrollback the daemon still holds, and no more. Attaching replays a session's history, but the daemon keeps only history.limit lines of it per session — 1000 unless the profile it was started with says otherwise. Lines that scrolled past that are gone, and there is no way to ask for them back.
    • A session sitting on the alternate screen has no scrollback to show. Attach while vim, less or htop is running and you get that program's screen, which never has history of its own; the shell's scrollback appears when the program exits.
    • Shells end with the daemon (see Stopping a daemon); the workspace comes back without them (see Surviving reboots).
    • ssh attach needs key or agent authentication. Contour never answers an ssh prompt — a password, a key passphrase, a second factor or an unknown host key — so run ssh USER@HOST once in a terminal first (see Remote hosts).
    • Images are not recoverable through tmux-mode replay (see the note under tmux interoperability).

    For the architecture behind all of this — the two protocols, the delta transport, the stable row identity in the grid — see the internals page.
