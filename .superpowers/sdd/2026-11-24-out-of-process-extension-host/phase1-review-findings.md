# Phase 1 whole-diff review — findings to fix (all of them)

1. (Important) Wasmtime lets a guest grow a table without limit; WAMR caps it. WasmtimeInstance.cpp:327 `wasmtime_store_limiter(store, memoryCap, -1, 1, -1, 1)` → table_elements and tables unlimited. Verified: `(table 1 funcref)` + `table.grow` by 10,000,000 succeeds (~92 MB RSS); `table.grow(ref.null, 0xFFFFFFFF)` would try ~32 GiB, bypassing memoryBytes; a huge initial table size gets through the same way. WAMR caps a table without declared max at max(2 × initial, 1024) (wasm_loader.c:2520 adjust_table_max_size). Fix: add a neutral `RuntimeLimits::tableElements` (pick the value so WAMR's behaviour and Wasmtime's agree — e.g. 1024 by default, documented) that both backends enforce (Wasmtime: limiter table_elements + tables = 1; WAMR: check declared table sizes at load / rely on its cap, and refuse an initial size above the limit with OutOfMemory or InvalidComponent consistently across both engines); contract cases `tableGrowthIsCapped` and `tableInitialSizeIsCapped`.
2. CPM local-package modes break the WAMR fallback (ContourThirdParties.cmake:473): with CPM_LOCAL_PACKAGES_ONLY=ON and no Wasmtime, CPM SEND_ERRORs; with CPM_USE_LOCAL_PACKAGES a found Wasmtime is discarded (499-504) instead of probed. Fix: when either variable is set, take the find_package + probe branch first.
3. Installed-Wasmtime probe lacks WAT, which the tests need (wasmtime_wat2wasm under WASMTIME_FEATURE_WAT; WasmtimeBackend_test.cpp:99). Fix: add WAT to the required list for the test target, or gate the test target on it (production code must not require WAT).
4. Installed Wasmtime DLL on Windows: `constexpr FeatureSetters` (WasmtimeBackend.cpp:97) takes addresses of __declspec(dllimport) functions — not constant expressions (clang-cl rejects). Fix: make the table non-constexpr (static const), or accept only a static system Wasmtime on WIN32. Prefer non-constexpr.
5. WAMR rejection messages stale (ContourThirdParties.cmake:270): the fatal error names only THREAD_MGR/hardware bounds checks, omits the feature-set rule and does not print `_wamr_rejected`; a probe that fails to COMPILE still reports "did not stop a call". Fix: include the reason and the feature rule; give compile failure its own reason.
6. Containment lint misses Wasmtime's C++ headers wasmtime.hh / wasm.hh (scripts/check-wasm-runtime-containment.py:59). Fix: `(wasmtime|wasm|wasi)\.hh?[>"]`; adjust the self-test.
7. ShimEnvironment can be built unusable (Preview1Shim.hpp:48,52): an empty std::function → bad_function_call inside noexcept → terminate. Fix: refuse empty callbacks at construction (complete-constructor rule) — e.g. WasmtimeRuntime::create returns RuntimeUnavailable, or ShimEnvironment gets a constructor requiring both; and make `clock` take `ClockId` instead of uint32_t.
8. `function()` narrower on Wasmtime than the interface says (WasmtimeInstance.cpp:352 vs WasmRuntime.hpp:183): document the all-i32 narrowing in the interface (both backends' callers only use all-i32 exports) or pin with a contract case — document it in WasmRuntime.hpp and add a contract case asserting the agreed behaviour on both engines.
9. Cleanups: MaxHostParameters = 17 duplicated (WasmtimeBackend.hpp:20, WamrRuntime.hpp:96) and WasmRuntime.hpp:120 names WAMR's copy → move one constant to the interface (WasmRuntime.hpp); EngineFeatures.hpp:77 claims "world check reports by name" though nothing outside the backends uses the table → fix the comment; the configure summary "Extension host engine: Wasmtime 48.0.10" (CMakeLists.txt:490, ContourThirdParties.cmake:533) is misleading while nothing ships it → reword to say the engine is available for the extension host (tests only for now).
